# n-dx 0.8.0 — Find your way

**Status: the lane is complete; three gate items remain.** See
[Release gate](#release-gate).

All six packages move `0.7.2 → 0.8.0`.

## What changed

### A new folder layout, resolved in one place

n-dx kept its state in three root dot-directories (`.rex/`, `.hench/`,
`.sourcevision/`) and five loose `.n-dx*` files, with roughly 380 source sites
naming those paths directly. 0.8.0 introduces a single container, `.ndx/`, and
one resolver that decides which layout a project is on.

- `resolveLayout` in `@n-dx/llm-client` is the single decision point; a `.ndx/`
  directory at the project root selects the new layout and its absence selects
  the legacy one, silently — an un-migrated project is not misconfigured.
- Each package gained a paths module that composes the resolver with its own
  filenames.
- `ndx init` writes the `.ndx/` layout for new projects.
- **`ndx migrate-layout`** moves an existing project when the operator chooses:
  it snapshots, `git mv`s the tracked paths so history follows, moves the
  untracked state, rewrites the `.gitignore` and `.gitattributes` blocks, and
  verifies — or restores.
- The per-user directory becomes `~/.ndx/`, with `NDX_HOME` as the override and
  `~/.n-dx/` plus `N_DX_HOME` still read as fallbacks.
- A policy test now rejects **new** literal `.rex/`, `.hench/`,
  `.sourcevision/` and `.n-dx*` paths in production source, with the remaining
  sites recorded in `tests/layout-literal-inventory.md` as a debt that may only
  shrink.

`.mcp.json` stays at the repository root, because the vendor CLIs read it
there, and task claims stay in the git common directory.

### Per-vendor agent models

`hench.model` is deprecated and ignored. `ndx work` resolves its model from
`--model`, then `hench.models.<vendor>`, then the `llm.*` fields. The dashboard
serves one model catalog per vendor and offers only the providers each vendor
supports.

### Command transparency

Interactive `analyze`, `plan` and `recommend` print a preflight banner saying
what the command will read, write and spend before it starts, with a pause the
operator can shorten via `NDX_PREFLIGHT_PAUSE_MS` or skip with `--yes`. Each
prints a run summary afterwards — files written, calls, tokens, cost.

Cost is reported only when it is known. An unpriced model or a provider that
reported no usage leaves the field unset, and the summary says "not recorded"
rather than `$0.00`.

### PRD storage

`rex tree-diff --json` diffs two PRD trees; `rex ready` marks items ready when
they have an automated or metric requirement and no open blocker; items carry an
assignee and `ndx work --mine` respects it. Whole-tree PRD rewrites are refused
off the default branch without `--allow-on-branch`.

## New configuration keys

Four keys are genuinely new — absent from the 0.7.2 schema, not merely unlisted:

| Key | Package | What it does |
|---|---|---|
| `hench.models.<vendor>` | hench | Agent-only model for `claude`, `codex`, `google` or `local`. Set in `.n-dx.json` (`.ndx/config.json` on the new layout), not through `hench config`. |
| `hench.batchMaxAgeHours` | hench | How old a batch session may get before it is retired. |
| `hench.batchMaxIdleHours` | hench | How long a batch session may sit idle before it is retired. |
| `hench.guard.memoryMonitor.spawnThreshold` | hench | Memory headroom below which the guard stops spawning. |

`hench.model` still parses, so existing configs keep loading, but it is ignored.

**A further 32 keys became visible without becoming new.** `hench config` listed
21 keys at 0.7.2 and lists 56 now. The schema already accepted the other 32 —
they worked if you hand-edited `.hench/config.json` and were invisible if you
did not, which is the gap 0.8.0 closed. They are not listed here as new
configuration, because calling them new would misdescribe what changed: the
setting did not arrive, the way to discover it did. `memory-monitor.ts` telling
operators to run a `hench config` command the CLI then refused is the case that
made it worth fixing.

## Redirects

PR B4 merged the navigation reorganisation: one navigation model, a next-step
Home panel, and tabbed Terrain and Architecture sections. Two view paths were
merged into a stage and redirect to it.

| Old path | Redirects to |
|---|---|
| `overview` | `analyze` |
| `rex-dashboard` | `work` |

Both remain registered views rather than being deleted, and the alias only fires
when its target is valid for that viewer. The case that covers: a rex-scoped
standalone viewer has no `work` stage, so `rex-dashboard` keeps rendering as its
own page there instead of redirecting nowhere.

The table lives in `packages/web/src/shared/view-routing.ts` as `VIEW_ALIASES`.

## Security

`pnpm audit` is clean: **0 critical, 0 high, 0 moderate, 0 low**.

Getting there needed two dependency overrides, so this release did not merely
confirm a clean scan:

| Advisory | Path | Resolution |
|---|---|---|
| `undici` — 11 advisories (3 high, 5 moderate, 3 low) | `sourcevision > jsdom > undici` | New override `undici@<8.10.2` → `^8.10.2` |
| `ip-address` — 4 moderate | `rex > @modelcontextprotocol/sdk > express-rate-limit > ip-address` | Existing override corrected from `ip-address@<10.5.0: ^10.5.0` to `<10.5.1: ^10.5.1` |

The `ip-address` entry is worth noting: an override already existed and was
pinning the vulnerable version. The advisory covers `<=10.5.0` while the
override only matched `<10.5.0`, so a transitive request for exactly `10.5.0`
was never rewritten. An override that looks present is not the same as one that
is effective.
