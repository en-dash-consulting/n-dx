Every child process gets the sanitized environment (#686, #635).

- Commands the repository owns no longer see your credentials. The test gate, post-task tests, `pnpm audit` / `pnpm outdated`, requirement validation commands, the cleanup typecheck, completion validation, rex's `verify_criteria` test command and the pair reviewer's fallback test run now run with the same credential filter as the agent's shell (`guard.env`), instead of inheriting the whole parent environment. A `guard.env.allow` entry the repository ships (`.hench/config.json` or the `hench` section of `.n-dx.json`) reaches these commands only while you trust the repository (`ndx trust accept .`). Entries in your git-ignored `.n-dx.local.json` always apply.
- Vendor CLI environments keep each vendor mode's credentials from one table. Codex keeps the variable named by the `env_key` of the model provider your own Codex config selects (`$CODEX_HOME/config.toml`, default `~/.codex/config.toml`), so Codex on Azure OpenAI starts with its key; a repository's `.codex/config.toml` and its n-dx config are never read for it. The Gemini CLI on Vertex AI (`GOOGLE_GENAI_USE_VERTEXAI` on) keeps `GOOGLE_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_PROJECT` and `GOOGLE_CLOUD_LOCATION`. A mode's names are kept only while that mode is active, and `ndx work` reports by name when an active mode has none of its credentials.
- A repository cannot choose which variable is sent as an API key, or where it is sent. `api_endpoint` (Claude, Codex, Google, and the legacy `claude` block) and `llm.google.apiKeyEnv` in the shared `.n-dx.json` apply only once you trust the repository; until then they are ignored with a warning, and the trust review lists them. The same fields in your `.n-dx.local.json` always apply, and `ndx config` now writes them there. A repository you trusted before that sets one of them reads as changed and asks again. `llm.google.apiKeyEnv` is now read by every loader, not only the auth preflight. `ndx config --test-connection` follows the same rule, so it no longer sends your Claude API key to an untrusted repository's endpoint. So does the Google auth check in `ndx auth`, `ndx init` and `ndx config llm.vendor google`: an untrusted repository's `apiKeyEnv` no longer picks which variable it sends.
- A repository cannot choose the vendor CLI binary n-dx runs. `llm.claude.cli_path`, `llm.codex.cli_path` and the legacy `claude.cli_path` in the shared `.n-dx.json` apply only once you trust the repository, for `ndx auth`, `ndx init`, `ndx config llm.vendor`, `ndx work` and the cross-vendor reviewer; until then they are ignored with a warning naming the field, and the trust review lists them. `.n-dx.local.json`, where `ndx config` writes `cli_path`, always applies. A repository you trusted before that sets one reads as changed.
- Nor can it through hench's `claudePath` or the dashboard's CLI version probe. A `claudePath` other than the bare `claude` in `.hench/config.json` or the `hench` section of `.n-dx.json` is listed by the trust review, and `ndx work` spawns it only once you trust the repository; `hench.claudePath` in `.n-dx.local.json` always applies, and `ndx init` now writes a discovered install path there instead of `.hench/config.json`. The dashboard's model catalog probes the binary runs use (`CLAUDE_CLI_PATH`, then the trust-gated `cli_path`) instead of reading `cli.claudePath` and `llm.codex.cli_path` raw from the project config.
- Nor through `cli.claudePath`. `ndx init` probes and registers MCP servers with the Claude binary before the trust review, so it reads `cli.claudePath` only from `.n-dx.local.json`, where `ndx config cli.claudePath` now writes it. One in the shared `.n-dx.json` is never run and is listed by the trust review; a repository you trusted before that sets one reads as changed. Move a hand-set shared value to `.n-dx.local.json`.
