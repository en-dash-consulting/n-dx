description: "Where the data is: `packFrameworkFacts(ctx, inventory)` (called in `packages/sourcevision/src/cli/commands/analyze.ts` around line 848, where `withEcosystem(..., packEcosystem(...))` builds sdlc-profile.json) returns per-file pack facts. Each carries optional `versionFloor` (`VersionFloorFact`: version, rule, construct, source, position) and `legacyConstructs` (`LegacyConstructFact[]`: rule, construct, status removed|deprecated|notice, deprecated?/removed?/changed? boundaries `{version, source}`, source, likely?, position `{line, column}`), defined in `packages/lang-kit/src/pack-contract.ts`. `packages/sourcevision/src/analyzers/pack-ecosystem.ts` aggregates them per language: `byLanguage` splits each language's facts into the application's own and third-party files (`FileEntry.thirdParty`) and drops mirror copies (`FileEntry.mirrorOf`). Reuse that split so the per-file list and the profile can never disagree.\n\nWhat to build:\n1. A new data file, `legacy.json` (add `legacy` to `DATA_FILES` in `src/schema/data-files.ts`, with a doc comment like `config`'s: written only when a pack produced such facts). Shape, keyed by lower-cased inventory language, every array sorted (files by path, uses by line then column):\n   `{ languages: { php: { files: [ { path, floor?: { version, rule, line }, uses: n, notices: n, removedIn: { \"7.0\": n }, deprecatedIn: { \"5.5\": n }, constructs: [ { rule, construct, status, line, column, deprecated?: \"5.5\", removed?: \"7.0\", changed?: \"x.y\", likely?: true } ] } ], thirdParty: [ same shape, only when non-empty ] } } }`.\n   Versions only, no URLs per use: the source pages already live once per rule in sdlc-profile.json. A file appears when it has a floor or at least one construct; `uses` counts removed+deprecated, `notices` counts notices, the same split pack-ecosystem uses. `removedIn`/`deprecatedIn` follow pack-ecosystem's definitions per file.\n2. Types in `src/schema/v1.ts` and validation in `src/schema/validate.ts`, beside the Sdlc ecosystem types.\n3. A builder (in `pack-ecosystem.ts` or a sibling `pack-legacy-files.ts`) and a writer following `writeConfigData` in `src/analyzers/pack-config-facts.ts`: canonical JSON via `toCanonicalJSON`; with no data, remove a legacy.json an earlier run left. Call it next to the sdlc-profile write in `analyze.ts`, reusing the same `packFrameworkFacts` result (no second fact read, no second parse). Runs without the imports phase (`--phase`, `sv narrate`) take facts the way the ecosystem does.\n4. Make sure anything that enumerates the analysis files (ALL_DATA_FILES consumers: manifest, export, MCP file listings, the web dashboard's file list, cleanup, `git`-ignore or tracked-file rules) handles an optional file the way it handles `config.json`; grep for `DATA_FILES.config` and `config.json` and mirror each place.\n\nInvariants: byte-identical output for a repository without legacy-construct or version-floor facts (no legacy.json, no other file changes); the per-file totals equal sdlc-profile.json's `ecosystem.<lang>.legacyConstructs` (files, uses, notices, per-rule uses and files, removedIn, deprecatedIn) and `versionFloors` (files with a floor per version) for the application's own files, and likewise for `thirdParty`; positions and versions only, never a code excerpt or literal value.\n\nTests: invented PHP fixtures only (no client code). Unit tests for the builder (sorting, own vs third-party, mirror dropped, a floor-only file, a notices-only file, totals equal `packEcosystem`'s for the same facts); a writer test (written, removed when empty, untouched otherwise); an integration test in `tests/integration/` on a small synthetic legacy PHP estate (the PR 12 end-to-end fixture can be reused if it fits) that skips through `tests/helpers/workspace-pack.ts` when the PHP pack cannot run. Docs: a short section in `docs/packages/sourcevision.md` beside the ecosystem docs and one line in `packages/sourcevision/AGENTS.md`'s PHP section naming legacy.json. Patch changeset for `@n-dx/sourcevision`.\n\nOut of scope: MCP or CLI views of the list, Rector rule mapping, new legacy rules, dynamic-code per file."
