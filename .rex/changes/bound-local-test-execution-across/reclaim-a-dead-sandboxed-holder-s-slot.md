description: "PR 3 (#1035) review by Hal, 2026-11-14 (thread 4570847987), [P1].\n\nProblem, on Linux with bwrap, via `run_command`:\n1. The agent runs `pnpm test`. bwrap gives it PID namespace A, and the runner takes the slot, recording `pidNamespace: A`, `outerPidNamespaces: [host]` and a small pid.\n2. The command overruns `commandTimeout`. `terminateProcessTree` kills the outer bwrap (`--new-session`, no signal forwarding), and `--die-with-parent` SIGKILLs everything in A. `finish()` never runs, so `holder.json` stays.\n3. The next confined run is in namespace B. B is neither A nor in the record's outer list, so rule 4a judges the record \"beside it: invisible, never judged dead\", and the run waits until its own timeout, as does every later confined run. Also, nsfs inode numbers are reused (an IDA allocator), so B often gets A's number back. Then `recorded === own`, and the old small pid matches B's own shell, pnpm or runner, so the record reads as alive.\n\nOnly an unconfined acquirer clears it. A vendor-CLI session, which uses one sandbox for the whole session, hits the same wall when a host holder dies mid-session. Hal reproduced it against the module with a fake `/proc`.\n\nFix (Hal's option a): hench runs on the host and can judge every record from the host view.\n- Export a `reclaimIfStale(slotDir)` from `packages/hench/src/process/validation-slot.ts`. It does one read of `holder.json`, judges `isValidationSlotHolderStale` from this (host) process's view, and if stale reclaims it with the existing `reclaimStale` and its lock. No record, or a live one: do nothing. It never waits and never throws; a failure is logged at most.\n- Call it before each confined spawn: in the `createToolSandbox` / `createVendorCliSandbox` wrappers (find where `wrapInSandbox` is invoked for tool children and for the vendor CLI). Use the per-host slot directory, `resolveValidationSlotDir`. Run it whatever `hench.testGate.hostSlot` says, because the runner takes the slot unconditionally; skip it when the slot directory does not exist.\n- For the vendor-CLI session (one sandbox for the session), also call it at each of hench's own validation steps, which run on the host, so a dead host holder is cleared there too.\n- Do not add a maximum wait (Hal's option b) or a flock (option c).\n\nAlso fix the A-number-reuse case: when the record's `pidNamespace` equals the reader's own and the reader is inside a sandbox (it has outer namespaces), the record's `bootedAt`/`startedAt` cannot tell a reused namespace apart. So treat a record in the reader's own namespace whose `startedAt` is earlier than the reader's own process start (or the sandbox start, if available) as not the reader's tree, and judge it by `reclaimIfStale` from the host instead. If that can't be done reliably, document the limitation in the rule 4a text and rely on the host reclaim above. Say which in the summary.\n\nTests:\n- a unit test with a fake `/proc`: a record from a dead sibling sandbox namespace is reclaimed by `reclaimIfStale` from the host view, while a contender in sandbox B would have waited;\n- a live record is left alone;\n- the sandbox wrappers call `reclaimIfStale` before spawning (unit-level, through a seam).\n\nUpdate the rule 4a text in the module header and mirror any protocol-visible change in `scripts/lib/validation-slot.mjs` (the runner copy) so the parity test still passes.\n\nOperator notes: you are on macOS; bwrap and real namespaces are Linux-only, so test through the fake `/proc` and seams. Build hench before the parity test. Run the slot tests, sandbox tests, the parity test and the static root policy tests. Add a patch changeset for `@n-dx/hench`. No `process.env.NDX_*` writes in tests."
