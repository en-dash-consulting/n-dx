Every wave 1 run so far used NDX_SANDBOX=off, and the runner's tests disable the tool sandbox, so nothing exercised the default path.\n\nFix (decided 2026-11-12): give the sandbox narrow access to exactly the slot directory, read and write, and nothing else in the ndx home.\n- In packages/llm-client/src/sandbox.ts, carve `<ndx home>/validation-slot/` out of the ndx-home denial for both sandbox kinds that run repository commands or agent shells (the tool sandbox and the vendor-cli sandbox), in both builders: the macOS SBPL profile (allow file-read*/file-write* on that subpath after the deny, since the masked block is last and wins) and the Linux bwrap builder. The directory holds only pids, tokens, timestamps and project paths, no credentials. Keep `auth.token`, the credential store and everything else in the ndx home denied. Resolve the slot directory the same way hench's `validation-slot-dir.ts` and scripts' `validation-slot.mjs` do (NDX_HOME / N_DX_HOME / home), and create it before building the profile if it does not exist, since the sandbox cannot grant a path that a child would have to create in a denied parent.\n- In scripts/lib/validation-slot.mjs and packages/hench/src/process/validation-slot.ts, check the nesting token by reading `holder.json` before any mkdir or write, so a nested acquire needs read access only.\n- If the sandbox still cannot reach the slot (an unexpected EPERM/EACCES), the runner must fail with a message that names the sandbox and the slot directory, not only \"Pass --no-slot\".\nThis widens the sandbox, so state in the change's commit message exactly which path is granted and why, and keep the existing sandbox policy tests (credential and ndx-home denial) passing; add assertions that `auth.token` and the credential store are still denied while the slot directory is allowed.\n\nTests:\n- An integration test with confinement enabled (macOS sandbox-exec; Linux bwrap when available;
