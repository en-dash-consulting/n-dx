title: "Reclaim a gone sandbox's slot record on a real Linux /proc"

summary: "On a real Linux machine, the validation slot can never be reclaimed after a sandboxed run dies, because the check counts any of the user's processes it cannot inspect as possibly the dead holder. Gates then wait forever behind a record nobody holds. This fixes the check to ignore processes that cannot be inside a sandbox."
description: "PR 3 (#1035) CI, first real Linux run (ubuntu-latest, non-root), run 43519677565. Two jobs fail on the same test in both slot implementations:\n- `packages/hench/tests/unit/process/validation-slot.test.ts` > \"acquireValidationSlot — PID namespaces (rule 4a) > on a real /proc, reclaims a gone sandbox's record despite other users' unreadable processes\"\n- `tests/e2e/validation-slot-parity.test.js` (both directions, the same case)\n\nEach fails with `ValidationSlotAbortedError: Gave up waiting for the validation slot after 10002 ms`. The test writes a holder record with `pid: 3, pidNamespace: \"pid:[1]\", outerPidNamespaces: [<own ns>]` and expects acquire to reclaim it.\n\nCause (from the code): `isAliveInInnerNamespace` in `packages/hench/src/process/validation-slot.ts` (and its twin in `scripts/lib/validation-slot.mjs`) scans every numeric `/proc` entry and readlinks `/proc/<n>/ns/pid` first. On a read error other than ENOENT, `isOwnedByThisUser` decides whether the entry counts as unreadable, and any unreadable entry makes the function return true (alive). On the runner, some of this user's own processes refuse `ns/pid`: readlink needs ptrace read access, which a non-dumpable or capability-holding process of the same uid denies, while `/proc/<n>` may still be owned by the uid. So the gone sandbox is always judged alive.\n\nFix, in both implementations, keeping them in parity:\n- Read `/proc/<n>/status` first; it is world-readable and needs no ptrace access. Its `NSpid:` line has one entry per PID namespace from the `/proc` mount's namespace inward. A process with a single `NSpid` entry is in the reader's own namespace and cannot be inside an inner (sandbox) namespace, so skip it without reading `ns/pid`.\n- Only for entries with two or more `NSpid` entries, readlink `ns/pid` to compare with the recorded namespace. Keep the existing rule that such a nested entry which cannot be read (other than ENOENT) and is owned by this user counts as possibly alive.\n- Match the pid against the last `NSpid` entry (or `NSpgid` for a group) as today. A `status` that cannot be read with ENOENT means exited, so skip it.\n- Update the rule 4a text in the hench module header, which documents the protocol for both implementations, to say entries whose `NSpid` has a single entry are skipped.\n\nTests:\n- The fake-`/proc` fixtures (`addProcess` and friends in `validation-slot.test.ts` and the parity test) must write a `status` with an `NSpid` line that reflects nesting. Inner-namespace processes get two or more entries.\n- Add a case: an own-user process with a single `NSpid` entry whose `ns/pid` is unreadable (chmod 000) does not keep the record alive.\n- Keep \"outside a sandbox, counts a process it cannot inspect as the holder\" passing: its process is nested (`addProcess(9003, INNER, 2)`), so give it a multi-entry `NSpid` and keep the expectation.\n- The real-`/proc` test only runs on Linux non-root and cannot run here (macOS). Reason from the code and say so.\n\nOperator notes: you are on macOS, so Linux-only cases will be skipped locally. Run the two changed test files plus `tests/e2e/validation-slot-parity.test.js` after building hench (`pnpm --filter @n-dx/hench build`). Run the static root policy tests. Add a patch changeset for `@n-dx/hench` describing the fix. No `process.env.NDX_*` writes in tests."
