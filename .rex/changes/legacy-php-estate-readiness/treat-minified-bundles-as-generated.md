summary: "Stop committed minified JavaScript from bloating the analysis: a test repository's call graph grew to 260 MB from twenty bundles."
description: "\"**Problem.** Committed minified bundles are common in legacy web apps (jQuery, plugins, built front ends). On an invented 346 MB probe, 20 minified JavaScript files of 2.7 MB each (role `asset`, under `public/js/`) were still parsed by the call-graph phase: **1,400,000 \\\"functions\\\", and `callgraph.json` was 260 MB** of the 516 MB analysis output; the whole analysis peaked at 1.75 GB RSS. Elsewhere, `js/app.min.js` outside a public directory was inventoried with role `source`. Minified code is third-party or build output, never something to map.\\n\\n**Fix.**\\n- Inventory classifies minified files as generated: `*.min.js`, `*.min.mjs`, `*.min.css`, `*-min.js`, `*.bundle.js` and source maps by name, plus a content check on the first bytes for a very long first line (for example any line over 2,000 characters in the first 64 KiB) on JS/CSS files that do not match by name. Use the existing generated-file mechanism (`generatedFilePatterns` / `generatedHeaders` in lang-kit configs, `analyzers/inventory.ts`).\\n- The call-graph phase, and any other per-function or per-symbol phase that would parse it (components, JS/TS imports if they parse bodies), skips files whose role is `generated` or `asset`. Check what `classifications`/zones do with them and keep them out of call-graph statistics.\\n- A repository with no minified files keeps byte-identical output.\\n\\n**Default and opt-in (requirement from a real scan, shape only):** committed minified bundles *outside* `vendor/` (for example a theme's `js/` folder, not under `public/`) produced 53–69 MB of `callgraph.json` per repository, while PHP was absent from it.
