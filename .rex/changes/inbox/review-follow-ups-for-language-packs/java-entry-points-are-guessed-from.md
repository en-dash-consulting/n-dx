description: "Verdict: should-fix (severity low). The Java LanguageConfig (packages/sourcevision/src/language/java.ts, entryPointPatterns) uses path heuristics (*Application.java, Main.java) because entryPointPatterns are path-only regexes. The task spec said entry points are \"classes with a public static void main\". Scenario: a CLI tool whose main class is com/acme/tool/Launcher.java is not an entry point; a non-runnable class named FooApplication.java is. Reachability: entryPointPatterns is not read by any analyzer today (grep src/ outside language/), so there is no wrong output yet; it becomes wrong once a consumer reads it. Options: (1, recommended) when the Java structure queries land, emit main-method declarations as entry points from the method query and use them in place of the name heuristic; cost is one query capture and a golden, no risk to other languages. (2) Read file content in a content-aware entry-point hook on LanguageConfig; wider contract change across all languages.\n\nImplementation brief (Java session, 2026-10-11; option 1):\n- Add an entry-point capture to packages/sourcevision/src/language/queries/java/methods.scm: a method_declaration named `main` whose modifiers include both `public` and `static`, with a void_type result and one formal parameter of type String[] or String... . Capture it as `@entry_point.main` (the declaration node) so the golden records it per file. No existing Java query uses text predicates (#eq?, #match?); confirm the runner (src/language/runner.ts, query.captures) honours them, and if it does not, keep the query structural and filter the captures in code with a unit test.\n- Remove the file-name heuristic: javaConfig.entryPointPatterns in src/language/java.ts becomes empty, and its doc comment says entry points come from the `entry_point.main` capture. Update tests/unit/language/java-config.test.ts (around line 155), which pins the old patterns. entryPointPatterns has no consumer outside src/language/ today, so nothing else changes.\n- Fixture: tests/fixtures/language-packs/java/src/Default.java already declares public static void main. Add a runnable class whose file name matches neither old pattern (e.g. src/com/example/tool/Launcher.java) and a non-runnable src/com/example/app/FooApplication.java with no main method, plus one near miss that must not match (e.g. a non-static `void main(String[] args)` or `public static int main(String[] args)`).\n- Out of scope: Java 25 instance main methods and compact source files (JEP 512). tree-sitter-java 0.23.5 cannot parse compact source files, and the grammar pin stays where it is.\n- Regenerate goldens only with `pnpm --filter @n-dx/sourcevision test:update-goldens`; never edit golden.json by hand. The script rewrites every pack's golden: the resulting diff must touch only tests/fixtures/language-packs/java/golden.json. Any change to another pack's golden or to a build-model golden means something else moved; stop and report it instead of committing it.\nBefore (PR 10 at fcc057981):\n  grep -c entry_point packages/sourcevision/tests/fixtures/language-packs/java/golden.json  -> 0\n  grep -n 'Application\\\\.java\\|Main\\\\.java' packages/sourcevision/src/language/java.ts  -> two entryPointPatterns\nAfter:\n  the same grep on golden.json -> Default.java and Launcher.java each carry an entry_point.main capture; FooApplication.java and the near miss carry none\n  entryPointPatterns for Java is empty\n  pnpm --filter @n-dx/sourcevision exec vitest run tests/unit/language tests/integration/language-pack-goldens.test.ts  -> passes\n  git diff --stat -- packages/sourcevision/tests/fixtures  -> only the Java fixture sources and the Java golden"
