Route tests: a task-less change and a task under an unassigned change in `others` both have inherited: false; a task inherited from an assigned task-less change that was later split still reads inherited: true. (2) Viewer: on a work-set branch, Work renders 'On this branch', then 'Not on a branch' with every open change in the PRD (about 120 groups on this repository), and only then Ready to run, which lands about 7,400 px down at 1440x900 — the run controls are effectively unreachable. Order the page 'On this branch', then Ready to run, then 'Not on a branch'; and show 'Not on a branch' paged like Ready to run (the first 10 groups, then 'Show all N'). On the default branch and an unassigned branch the page stays as it is today. Viewer test for the order and the paging. Have the options read say whether the current branch has a work set and offer stacking only then; the server refuses base 'current' off a work-set branch with 400 (add the route test if it is not there). Viewer test: on a feature branch with nothing assigned, no stacking choice. (4) After a successful Start a branch (checkout switched), the page kept showing the old branch's state — no 'On this branch' and the unnarrowed Ready to run (63 rows) — until a full reload; the server's work-set read was already correct. The dialog fires announceBranchSwitched() and onSwitched, but neither the work-set section nor Ready to run re-reads. Make both (and the PRD data the page shows) re-read on a switch, e.g. by having Ready to run and the work-set section listen for the BRANCH_SWITCHED_EVENT that use-git-status.ts already listens for. Viewer test: after a switched start, the work-set section and Ready to run re-fetch.
