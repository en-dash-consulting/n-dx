description: "Builds on 6fc82dbd (a18d53805): `src/analyzers/jev-split.ts` `askSplittingWhenTooLarge` halves a refused item range and returns items too large on their own. Today `typed-findings.ts` (TYPED_PER_REQUEST 20) and `classify.ts` (LLM_BATCH_SIZE 30) size batches by count, so on a large estate requests are sent, refused and re-sent. And an item refused on its own keeps its derived result unjudged.\n\nThree layers, splitting staying as the backstop:\n\n1. **Size ceiling before sending.** Add `packBySize<T>(items, sizeOf: (item) => number, ceiling): T[][]` to jev-split.ts. It packs items in order into chunks whose summed `sizeOf` stays under the ceiling, still capped by the existing count. An item over the ceiling alone gets a chunk of its own. Size is the UTF-8 byte length of the item's JSON contribution, plus the share of state the chunk adds once (for typed findings, each distinct scope's `buildZoneEvidence` entry counted once per chunk). Measure bytes, not tokens; no tokenizer.\n   - The ceiling is one exported constant (`JEV_REQUEST_BYTE_CEILING`) with a comment on how it was chosen. TypeSafe does not publish its limit, so pick it from data: the reference repository's deep run's successful finding.judge requests averaged about 22k input tokens. Log each request's byte size and whether it was refused, at debug level only.\n   - Overridable through `sourcevision.jev.requestByteCeiling` in project config, read the way other sourcevision config is.\n   - typed-findings and classify pack with it, then send each chunk through `askSplittingWhenTooLarge` as now.\n2. **Splitting stays the backstop.** It covers a wrong ceiling, a later change in TypeSafe's limit, and a limit on the answer rather than the request.\n3. **Trimming for a lone oversized item.** In `askSplittingWhenTooLarge`, take an optional `trim(item, level) => T | undefined` callback. When a single item is refused, retry it at trim levels 1, 2, … until it is answered or `trim` returns undefined. Only then is it left out.\n   - typed-findings trim order, applied to that request's zone evidence: level 1 drops `headers`; level 2 also drops `declarations` and `exportedSymbols`; level 3 cuts `files` to 10; level 4 cuts the finding's `edges` to 4. Classify items are a path plus 3 signals and need no trimming.\n   - Trimming is deterministic, so the judgment cache keys stay stable. Never summarize with a model: that is a paid call to work around size, it gives a different text each run (cache misses), and Jev would judge a paraphrase instead of the edges.\n   - Record on the finding that it was judged on trimmed evidence, e.g. evidence detail \"judged on trimmed evidence (level 2)\" or a `trimmed` count in the summary line, so a reader knows.\n   - The too-large-alone warning now counts only items left out after every trim level.\n\nOperator note: a classification request repeats the whole archetype catalog once per file question. That is TypeSafe's API shape; do not change the request format here. Mention it in jev-split.ts's module comment as the largest size driver for classify.\n\nTests (invented data, askJev mocked):\n- `packBySize`: order kept, ceiling respected, count cap respected, an oversized item gets its own chunk, shared state counted once per chunk.\n- typed-findings: with a small ceiling, findings go out in more requests with no refusals. A lone finding refused untrimmed and accepted at level 2 is judged, and its evidence detail says so. A finding refused at every level keeps its derived severity, and the warning counts it.\n- classify: packing by size produces the same results as count batching when everything fits.\n- Byte-identical output when every request fits under the ceiling and the count cap.\n\nChangeset: patch `@n-dx/sourcevision`. Document `sourcevision.jev.requestByteCeiling` in docs/packages/sourcevision.md beside the other sourcevision config keys."
