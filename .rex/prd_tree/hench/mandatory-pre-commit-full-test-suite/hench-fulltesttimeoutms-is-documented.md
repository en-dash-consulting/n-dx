description: "Severity: medium. Verdict: must-fix (real, reachable, actively misleads the operator into the opposite of the intended action; the fix is two strings).\n\n## The defect\n\nThe `hench.fullTestTimeoutMs` knob added by 0ce620c2 is documented as defaulting to 300000 (5 minutes) in both operator-facing places. The actual default is 900000 (15 minutes).\n\nWrong:\n- `packages/core/config.js:1628` — \"run fails (default: 300000 - 5 minutes; 0 means no limit)\". This block is live help text printed by `ndx config --help`.\n- `packages/hench/src/schema/v1.ts:238` — \"Default: 300000 (5 min).\" on the `HenchConfig.fullTestTimeoutMs` field.\n\nRight:\n- `packages/hench/src/schema/validate.ts:84` — `fullTestTimeoutMs: z.number().int().nonnegative().optional().default(900_000)`\n- `packages/hench/src/tools/test-runner.ts:485` — `export const DEFAULT_TEST_GATE_TIMEOUT_MS = 900_000`\n\n`packages/hench/tests/integration/test-gate-timeout-config.test.ts:35` asserts the loaded config equals `DEFAULT_TEST_GATE_TIMEOUT_MS`, confirming 900000 is what actually applies.\n\n## Failure scenario\n\nAn operator's suite takes 7 minutes and the gate kills it. They run `ndx config --help`, read \"default: 300000 - 5 minutes\", and set `hench.fullTestTimeoutMs = 600000` believing they have doubled the budget. They have in fact LOWERED it from 15 minutes to 10 - the suite that was already comfortably inside the real default now has less headroom than before they touched anything, and the gate keeps killing it. Because a gate timeout fails the run, this aborts tasks whose work is already done and committed, which is the exact outcome the field's own docblock says it exists to prevent.\n\nThe mirror case: a gate killed at 15 minutes that the operator attributes to a 5-minute limit and cannot reconcile with the config they are reading.\n\n## Provenance (in scope, not pre-existing)\n\n`origin/main` already carried a stale `/** Timeout for the test command in ms. Default: 300_000. */` at `test-runner.ts:452` beside a `TEST_GATE_TIMEOUT = 900_000` constant. This branch FIXED that line - and then propagated the wrong 300000 into two new operator-facing surfaces. 300000 is the correct default for the unrelated `commitMsgTimeoutMs` field two docblocks away (`v1.ts:281`), which is the likely source of the copy.\n\n## Reachability (Pass 2)\n\nReachable through `ndx config --help`, the documented discovery path for the knob, and through any editor hovering `HenchConfig.fullTestTimeoutMs`. Not covered by any test: the schema tests assert the code's 900000 against itself, so the prose can drift freely.\n\n## Solution options\n\n1. **Correct both strings to 900000 / 15 minutes (recommended).** Two lines. Cost: near zero. Risk: none. This is the whole fix for the reported defect.\n\n2. **Additionally, stop the two constants drifting again.** `validate.ts` mirrors the literal 900_000 rather than importing `DEFAULT_TEST_GATE_TIMEOUT_MS`, because a schema -> tools import would invert the layering (the code comment says so, correctly). The right guard is therefore a test asserting `HenchConfigSchema.parse({}).fullTestTimeoutMs === DEFAULT_TEST_GATE_TIMEOUT_MS`, not a refactor. Cheap, and it is the assertion that would have caught this.\n\n3. **Adjacent, same edit, optional.** `packages/hench/src/agent/lifecycle/shared.ts:2034-2040` prints the gate timeout only when it differs from `DEFAULT_TEST_GATE_TIMEOUT_MS`, so an operator who deliberately sets 900000 gets no confirmation their setting took effect. Printing whenever the value is explicitly configured costs one condition. Not required to close this task.\n"
