description: "#539 item 1, main part. Task 4 of 7. It depends on task 2 (`FinalizeRunOptions.gateBase`); task 3's flake re-run applies automatically. Related: #504 (still open; this does not close it).\n\n**The problem.** A run whose agent finished, committed, and asked for completion can still fail at the test gate. The completion is then held, not applied. The retry (`ndx work --task=<id>`) starts a full agent session anyway:\n1. The agent finds nothing to edit.\n2. `isReadOnlyRefusal` fires.\n3. Hench re-spawns cold (cli-loop.ts ~2484, 2683-2694).\n4. The cold session re-verifies everything.\n5. Then the gate runs again.\n\nThe retry of 5b8fc246 ran the full suite three times this way.\n\n**What exists today** (all paths under packages/hench/src):\n- **Held resolution.**\n  - `finalizeRun` (agent/lifecycle/shared.ts:3485) reads the hold with `readCompletionHold` (:3264, via `claims.pendingCompletion(taskId)`, process/task-claims.ts:244).\n  - On a failed gate it stamps `run.completionHold = {outcome: \"not-applied\", resolutionType?, resolutionDetail?, requestedAt}` (:4173-4179) and prints \"Its resolution is kept on the run record for the retry\" (`reportCompletionNotApplied`, :3307/3316).\n  - The rex claim does NOT keep it. A new run starts with nothing held (`packages/rex/src/store/claims.ts:427-434`, `recordPendingCompletion` at :479).\n  - So after the failed run, the held resolution exists only on the old run record, and **nothing reads it today**.\n- **Applying a resolution on green.** `updateCompletedTaskStatus(store, taskId, run, held)` (shared.ts:2682, called at :3964-3976), then `commitCompletionMetadata`. A failed run resets the task to pending (`resetInProgressTaskIfFailed`, :3095).\n- **Run record fields** (schema/v1.ts:1355): `status`, `startHead`, `branch`, `testGate`, `review` (RunReviewRecord :1220), `commits: {sha, subject}[]` (from `collectRunCommits` startHead..HEAD, shared.ts:3421, set at :4148), `completionHold` (:1708/1752), `structuredSummary.filesChanged`. `run.error` begins \"Test gate failed\" on a gate failure.\n- **The retry flow.**\n  - `runOne` (cli/commands/run.ts:1328) loads `listRuns(henchDir)` (newest first) and calls `cliLoop({... runHistory, claims, reviewPass, reviewOptional})` (:1392).\n  - `cliLoop` (agent/lifecycle/cli-loop.ts:1955) runs, in order: `prepareBrief` (claims the task) at 1969, `transitionToInProgress` at 2002, `initRunRecord` at 2022, `captureStartingHead` and the baselines at 2100-2106, the heartbeat at 2129, the commit-msg watcher, `ensureWarmParent` at ~2286 (may spawn an orientation session), the spawn loop at 2399, and `finalizeRun` at 2766.\n  - **The short-circuit point** is after the baselines (~2106) and before the heartbeat and `ensureWarmParent`.\n- **The gate's skip trap.** `runTestGate` returns `ran:false, passed:true` when `filesChanged` is empty (test-runner.ts:824-831). `finalizeRun` derives `filesChanged` from `discoverChangedFiles({startingHead})` (:3566). On a retry, startingHead equals HEAD, so the gate would \"pass\" without testing. The gate-only path MUST pass the earlier run's start commit as `gateBase` and as the diff base for `filesChanged`.\n- **Git helpers.**\n  - `getCurrentHead` and `exec` are in process/exec.ts (re-exported from prd/llm-gateway.ts).\n  - `findUncommittedWork` is in agent/lifecycle/uncommitted-work-gate.ts:284 and excludes hench artifacts.\n  - No `merge-base --is-ancestor` helper exists. Add one next to the others, using `exec`, not node:child_process.\n\n**Build.** Put the decision and execution in a new module, for example agent/lifecycle/gate-only-retry.ts.\n\n1. **Eligibility.** Write a pure function over the run history plus git facts:\n   - The task's most recent run (`runHistory` filtered by taskId, newest first) has all of:\n     - `status === \"failed\"`;\n     - `testGate.ran === true && testGate.passed === false`;\n     - `completionHold.outcome === \"not-applied\"` with `requestedAt`;\n     - a `startHead`;\n     - non-empty `commits`.\n   - Its last commit is an ancestor of HEAD (`git merge-base --is-ancestor`).\n   - The working tree is clean by `findUncommittedWork`.\n   - The current branch equals the run's `branch` when one was recorded.\n   - **Loop guard:** the most recent run is NOT itself a gate-only retry. If a gate-only retry fails at the gate again, the next retry runs the agent normally, so it can fix a real failure.\n   - **Gate base:** the earliest `startHead` among this task's runs that is still an ancestor of HEAD. Fall back to the held run's `startHead`.\n   - Every ineligible case falls through to today's path. Log one line saying why only when a held run exists but was not eligible.\n2. **Execution in `cliLoop`** at the short-circuit point. When eligible:\n   - Print one line naming the source run, its commits and the base.\n   - Set a new top-level `run.gateOnlyRetry = {sourceRunId, base, commits}`. It needs a zod RunRecordSchema entry; `tests/unit/schema/run-record-schema-drift.test.ts` enforces it.\n   - Copy the source run's `structuredSummary` and summary. `finalizeRun` only gates when `run.structuredSummary` exists.\n   - Re-record the held resolution as this run's pending completion, through the rex gateway (`recordPendingCompletion` or the TaskClaims equivalent), so `finalizeRun`'s normal hold path applies it on green. Do not call `updateCompletedTaskStatus` directly.\n   - Set the run completed as the agent path would, then call `finalizeRun` with `gateBase` set.\n   - No heartbeat-driven agent, no `ensureWarmParent`, no spawn, no read-only refusal, no cold re-spawn.\n3. **Review (`--review`).**\n   - If the source run has a `review` with no `failed`, `unrepairedMustFixCount === 0`, and HEAD has no commits after the source run's last recorded commit, copy it onto this run with `inheritedFrom: <sourceRunId>`. The missing-review refusal (`reviewNeverRan`, shared.ts:3824) is then satisfied truthfully. Note the field in RunReviewRecord and its zod schema.\n   - Otherwise run the review pass fresh with no session to resume (`runAdversarialReviewPass`, cli-loop.ts:1415; the non-Claude path already runs it unresumed) before `finalizeRun`.\n   - If wiring the fresh review is impractical, fall back to the normal path when a review is required and none can be inherited. Print why, and note it in your log.\n4. **API provider.** If `agentLoop` (agent/lifecycle/loop.ts) has an analogous point, wire the same helper in. Otherwise leave it on today's path and note that in your log.\n\n**Tests** (integration, following `tests/integration/gate-holds-completion.test.ts` and `read-only-refusal-retry.test.ts`, which mock `runTestGate` via `vi.doMock`).
