  - "`ndx analyze` runs a non-critical readiness phase that writes `.sourcevision/readiness.json` and registers it on `manifest.json`; a failure in the phase degrades the affected dimensions to `unknown` and never fails the analysis."
  - "Every dimension reports `covered`, `partial`, `missing` or `unknown`; `unknown` is only emitted with a populated `reason`, and no dimension reports `missing` when the probe backing it could not run."
  - "Every non-`unknown` verdict carries at least one evidence entry with a project-relative path; no verdict is asserted without one."
  - "The tests dimension reports the discovered test command, per-zone test presence and the zones with zero test files, and cites existing bloat findings by reference rather than re-deriving them; coverage is reported only when a coverage report is found on disk, and its absence is a stated gap rather than a reported zero."
  - "The rerun-safety dimension reports destructive commands with `path:line`, non-idempotent migration and unguarded-write sites, CI jobs lacking a concurrency group, and whether dependency vulnerability scanning runs in CI as opposed to merely being installed."
  - "The deploy dimension parses CI workflow definitions for GitHub Actions, GitLab CI, Bitbucket Pipelines and CircleCI into jobs classified as test, publish or deploy with their triggers and target environments; a provider file that is present but unparseable is reported as a parse failure with its path, never as \"no deploy configured\"."
  - "The deploy dimension names the deploy targets it found, states explicitly when no deploy step exists, and reports the last git tag with its date plus the version of every package, flagging any drift between them."
  - "Deployment targets declared under `sourcevision.readiness.deployments` and monitors declared under `sourcevision.readiness.monitors` in `.n-dx.json` are rendered as named links; both validate against one shared schema, and a malformed entry is surfaced as a config warning rather than silently dropped."
  - "No network call and no LLM call is made anywhere in the readiness phase, including for live deployment state; `analyze` wall-clock on this repo is unchanged within noise."
  - "The infra dimension inventories infrastructure-as-code and container surfaces and reports unpinned actions, floating image tags, missing or stale lockfiles, inline secrets, and absent health-check, non-root and restart-policy affordances, each with its evidence path."
  - "The monitoring dimension distinguishes a dependency being present from it being initialized in source, reports the structured-versus-`console` logging ratio, and reports whether a health or readiness endpoint is routed, reusing `route-detection.ts` rather than re-scanning."
  - "Every gap in a `partial` or `missing` dimension projects into a `NextStep` with a suggested action concrete enough for `ndx plan` to turn into a PRD task; the widened `NextStep` category union validates in `schema/validate.ts` and every existing consumer handles the new values."
  - "`get_readiness` is exposed on the SourceVision MCP server alongside `get_next_steps` and `get_findings`, and returns the same artifact the dashboard renders."
  - "A Readiness view shows all five dimensions with status, evidence, gaps, per-package last release and the declared deployment and monitor links; its SourceVision imports pass through `packages/web/src/server/domain-gateway.ts`."
  - "Readiness gaps do not enter the zone-findings stream and do not alter any zone health score."
description: "`ndx analyze` today answers \"how is this code structured\" but not \"is this safe to ship, and is it already shipped.\" Add a readiness pass to SourceVision that scores five operational dimensions, states the evidence behind every verdict, and feeds the gaps back as actionable next-steps rather than prose.\n\nShape: a seventh phase in `executePhases` (packages/sourcevision/src/cli/commands/analyze.ts), non-critical like `callgraph`, writing `.sourcevision/readiness.json` and registering it on `manifest.json`. Detectors follow the existing `project-profile.ts` pattern — cheap on-disk probes returning typed `{ kind, evidence }` records. No LLM, no network.\n\nArtifact shape: `dimensions[]` with fixed ids (`tests`, `rerun-safety`, `deploy`, `infra`, `monitoring`), each carrying `status` (covered/partial/missing/unknown), `reason`, `evidence[]` of `{ path, kind, detail }`, and `gaps[]` of `{ id, severity, text, suggestedAction }`; plus `release` (per-package versions, last tag and date) and `pointers[]` (declared external links).\n\nWhat already exists and must be reused rather than re-derived: bloat findings from `callgraph-findings.ts` (unused exports, god functions, fan-in hotspots); `verify_criteria` (rex MCP) for acceptance-criteria-to-test mapping; `detectReleaseInfrastructure()` and `detectCiSurfaces()` in `project-profile.ts`; `route-detection.ts` for health-endpoint presence; and `ndx plan`, which already turns sourcevision output into PRD proposals.\n\nWhat is genuinely new per dimension — tests: test-command discovery, per-zone test presence, coverage-report ingestion. Rerun safety: destructive-command scan, idempotency and locking markers, dependency-audit wiring, high-confidence secret patterns. Deploy: CI workflow semantics (which jobs test, publish, deploy; triggers; environments), deploy-target naming, last-release reporting. Infra: IaC and container surface inventory, supply-chain pinning, secrets handling, container hygiene, resilience affordances. Monitoring: error-reporting / metrics / tracing detected as initialized rather than merely installed, structured-vs-console logging ratio.\n\nSettled design decisions:\n- Live deployment state and external monitors are **declared, not fetched** — both live under one `sourcevision.readiness` namespace in `.n-dx.json` (`deployments[]`, `monitors[]`, sharing one shape and one validation path), alongside the existing `sourcevision.isoMap` precedent for facts no import graph can show. This keeps the readiness phase offline and keeps the configuration condensed and recognisable as a SourceVision addition.\n- All four CI providers (GitHub Actions, GitLab CI, Bitbucket Pipelines, CircleCI) are parsed up front rather than GitHub-only, so a supported provider never silently contributes missing data. An unparseable file is reported as a parse failure, never as absence.\n- Readiness gaps live in `readiness.json` and project *into* next-steps; they are not injected into the zone-findings stream, which is zone-scoped and LLM-enriched. Mixing them would corrupt zone health scores.\n\nHonest limits to preserve in the output: SourceVision can tell whether tests exist, run, and where the holes are — not whether they are good. Infra analysis is configuration review, not a pentest or CVE scan. Both should point elsewhere rather than overclaim.\n\nGoal: one place to read whether this project is safe to ship, with every gap actionable by `ndx plan`."
