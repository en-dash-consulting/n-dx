description: "**Severity:** medium — **Verdict:** should-fix\n\nCross-skill generalization of task `13e50500`, which fixed this for `/ndx-adversarial-review` only. That task's plan turned up the wider pattern; this item owns the fix for the rest and the test that would have caught all of them.\n\n**Failure scenario.** A skill tells the assistant to draft \"title, description, and acceptance criteria\" without naming `add_item`'s parameters. The assistant writes the criteria into `description` prose and leaves `acceptanceCriteria` empty. `verify_criteria` (rex MCP) and the dashboard's requirements view both read the array, so criteria that live in prose cannot be mapped to tests, cannot be checked by a later review, and do not render. The item looks complete and is quietly unverifiable.\n\n**Evidence — per-skill, verified by reading each body.** The gaps differ, so the fix is not identical across the three. An earlier version of this item showed a bare named/absent table, which overstated the gap for `ndx-capture` and `ndx-reshape`: both cover some fields behaviourally through prose steps even though they never name the parameter.\n\n- **`ndx-plan.md` — weakest, and it creates items in bulk.** Step 7 says only \"create it with appropriate descriptions, acceptance criteria, and parent placement\". No parameter is named, no `level` guidance is given, and `priority` and `source` are never mentioned. Every proposal it accepts is filed with a guessed level and, most likely, criteria in prose.\n- **`ndx-capture.md` — mostly covered behaviourally; one real gap.** Step 3 directs level selection, step 4 directs parent matching, and the \"Always do these\" section covers priority and `blockedBy`. Its genuine defect is acceptance criteria: step 5 says \"Draft the item: title, description, acceptance criteria\" without directing them into the `acceptanceCriteria` array, so they can land in `description`. `source` is also never set.\n- **`ndx-reshape.md` — narrowest scope.** It names `level`, but only for `edit_item` (\"Change levels with `edit_item` using the `level` field\"), not for the `add_item` calls that create new parent containers. Since it creates containers rather than work items, `acceptanceCriteria` matters less here; the real gaps are `level` and `parentId` on the containers it creates.\n- **`ndx-adversarial-review.md`** — fixed by `13e50500`; names all of `title`, `level`, `parentId`, `description`, `priority`, `acceptanceCriteria`, `tags`, `source`.\n\nThe schema being written against is `packages/rex/src/cli/mcp.ts:115-129`: `title` and `level` required; `parentId`, `description`, `priority`, `acceptanceCriteria`, `tags`, `source`, `blockedBy` optional.\n\n**Reachability.** Every item these three skills create. `/ndx-capture` is the primary path for filing work from conversation; `/ndx-plan` files in bulk.\n\n**Possible solutions.**\n1. *Recommended.* Give each skill the parameter mapping it actually needs rather than one identical table: `ndx-plan` needs the full table most urgently; `ndx-capture` needs `acceptanceCriteria` and `source` named, since level/parent/priority are already handled in prose; `ndx-reshape` needs `level` and `parentId` named for its container-creating `add_item` calls. Then add the general test below.\n2. Full table in all three, copied from `/ndx-adversarial-review`. Uniform and simpler to review, but adds guidance to `ndx-capture` and `ndx-reshape` that duplicates steps they already have, which is how prose skills get bloated.\n3. `ndx-plan` only, on the grounds that it is the one with no coverage at all. Cheapest; leaves `ndx-capture`'s criteria gap, which is the highest-traffic path.\n\n**The test that belongs with this work.** A structural assertion, derived from the manifest rather than hardcoded, that any skill body containing `add_item` also names `level` and `acceptanceCriteria`. It fails today on all three skills above, which is why it was not added under `13e50500` — landing it there would have left the suite red on work outside that task's scope. Model it on `tests/e2e/skill-run-recording.test.js`, which uses the same derive-from-manifest approach so a future skill is covered the moment it is added."
