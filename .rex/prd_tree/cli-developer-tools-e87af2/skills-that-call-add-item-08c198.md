description: "**Severity:** medium — **Verdict:** should-fix\n\nCross-skill generalization of task `13e50500`, which fixed this for `/ndx-adversarial-review` only. That task's plan turned up the wider pattern; this item owns the fix for the rest and the test that would have caught all of them.\n\n**Failure scenario.** A skill tells the assistant to draft \"title, description, and acceptance criteria\" without naming `add_item`'s parameters. The assistant writes the criteria into `description` prose and leaves `acceptanceCriteria` empty. `verify_criteria` (rex MCP) and the dashboard's requirements view both read the array, so criteria that live in prose cannot be mapped to tests, cannot be checked by a later review, and do not render. The item looks complete and is quietly unverifiable. `level` is a required parameter with no default, so it is also guessed per run and drifts between them.\n\n**Evidence.** Measured across the canonical bodies in `packages/core/assistant-assets/skills/` that call `add_item`:\n\n| Skill | `level` | `acceptanceCriteria` | `priority` | `parentId` |\n|---|---|---|---|---|\n| `ndx-capture.md` | named | **absent** | named | **absent** |\n| `ndx-reshape.md` | named | **absent** | **absent** | **absent** |\n| `ndx-plan.md` | **absent** | **absent** | **absent** | **absent** |\n| `ndx-adversarial-review.md` | fixed by `13e50500` | fixed | fixed | fixed |\n\nNot one skill named `acceptanceCriteria` or `parentId` before `13e50500`. `ndx-plan` — which creates items in bulk — names none of the four.\n\nThe schema they are being written against is `packages/rex/src/cli/mcp.ts:115-129`: `title` and `level` required; `parentId`, `description`, `priority`, `acceptanceCriteria`, `tags`, `source`, `blockedBy` optional.\n\n**Reachability.** Every item any of these three skills creates. `/ndx-capture` alone is the primary path for filing work from conversation.\n\n**Possible solutions.**\n1. *Recommended.* Give each of the three the same explicit parameter table `13e50500` added to `/ndx-adversarial-review`, adjusted for what each skill knows — `ndx-plan` proposes many items so its table should stress `parentId` and `level` per proposal; `ndx-capture` already determines level and priority and mainly needs `acceptanceCriteria` and `parentId` named; `ndx-reshape` mostly moves items, so it needs the mapping only where it creates containers. Then add the general test below.\n2. Table for `ndx-capture` only, on the grounds that it is the highest-traffic creator, and leave the others. Cheaper, but leaves `ndx-plan`'s bulk-created items unverifiable, which is the larger volume.\n\n**The test that belongs with this work.** A structural assertion, derived from the manifest rather than hardcoded, that any skill body containing `add_item` also names `level` and `acceptanceCriteria`. It fails today on all three skills above, which is why it was not added under `13e50500` — landing it there would have left the suite red on work outside that task's scope. Model it on `tests/e2e/skill-run-recording.test.js`, which uses the same derive-from-manifest approach so a future skill is covered the moment it is added."
