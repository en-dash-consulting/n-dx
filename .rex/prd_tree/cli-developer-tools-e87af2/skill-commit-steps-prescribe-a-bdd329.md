description: "**Severity:** medium — **Verdict:** should-fix (captured from /ndx-adversarial-review of branch `chore/pr-329-review-followups`, 2026-08-25)\n\n**Failure scenario.** Every committing skill instructs the assistant to build its commit message this way:\n\n```sh\ngit commit -m \"$(cat <<'EOF'\n<subject>\n\nN-DX: skill/<name>\nCo-Authored-By: En Dash's n-dx <n-dx@endash.us>\nEOF\n)\"\n```\n\nThere is no heredoc and no `$(...)` command substitution in PowerShell or cmd.exe. A user on Windows without Git Bash gets a parse error at the final step of the skill, after all the real work is done.\n\nThe louder failure is not the worst one. An assistant that recovers by improvising different quoting can reflow or drop the trailer block, and `packages/core/commit-trailers.js:5-11` documents that a missing `Co-Authored-By` fails **silently**: the commit succeeds, `packages/web/src/server/merge-history.ts` (`COAUTHOR_RE`) never matches it, and the commit is invisible to both the dashboard's merge graph and GitHub's contribution graph. Nothing reports the loss. The obvious portable workaround — repeated `-m` flags — makes this worse, not better: git joins them with blank lines, splitting the trailer block into separate paragraphs so git stops recognising it as trailers at all.\n\n**Evidence.** `packages/core/assistant-assets/skills/ndx-adversarial-review.md:143`, `ndx-capture.md:19`, `ndx-config.md:26`, `ndx-plan.md:23`, `ndx-reshape.md:33` — five canonical bodies, each with `.claude/` and `.agents/` copies.\n\n**Observed live, 2026-08-25.** The `/ndx-capture` run that filed this item hit the defect and got away with it. Its commit step ran this exact heredoc and succeeded — commit `48c2b5c1`, both trailers parsed correctly — **only because Git Bash happened to be installed on the machine.** The same session had already proved the shell is not there by default: `pnpm test` in `packages/hench` run from PowerShell on that machine fails 7 cases because `sh` is unresolvable (see task `9a38b74b`). So one shell on one machine silently decided whether the skill's final step worked, and nothing in the skill or the toolchain checks which shell it got.\n\nThe ordering is what makes this worse than a normal portability bug. The commit step is the **last** step: by the time it fails, `add_item` has already written every PRD item to `.rex/prd_tree/`. A Windows user without Git Bash gets a parse error on top of a dirty working tree full of completed work, with no instruction covering that state.\n\n**Git Bash cannot be assumed, and this is the crux.** It is not part of Windows. It arrives only with Git for Windows, which installs `sh.exe` under `C:\\Program Files\\Git\\usr\\bin` — a directory Git Bash puts on PATH and PowerShell/cmd.exe do not, even on a machine where Git itself is installed and working. So the dependency is invisible: `git` resolves fine, `git commit` from the skill does not. And `ndx init` ships these bodies into arbitrary repositories on arbitrary machines, so \"it works on the maintainer's box\" carries no information about anyone else's. `tests/shell-spawn-inventory.md:5-7` already states this exact fact for the test suite; the skill bodies never got the same treatment.\n\n**Scope split, and why they are folded together.** The four older bodies are pre-existing — the branch diff does not touch those lines. `ndx-adversarial-review.md` is new on this branch and introduced a fifth copy. They are one item because the fix is a single find-and-replace across the canonical directory plus one regression test; splitting it would mean fixing the same line five times in two passes and leaving a guard that four bodies fail.\n\n**Why this should have been caught.** The same branch added `tests/e2e/skill-portability.test.js`, whose docblock states the principle exactly — \"Skill bodies are installed by `ndx init` into arbitrary repositories, so an instruction that works here is not automatically an instruction that works\" — and guards one instance of it (`date -Is` must be paired with `Get-Date`). The new skill's own Step 1 *is* platform-neutral about the timestamp. Only the commit step is not, and the portability test does not look for heredocs.\n\n**Reachability.** Every run of `/ndx-adversarial-review`, `/ndx-capture`, `/ndx-config`, `/ndx-plan`, or `/ndx-reshape` that reaches its commit step, on any machine whose shell is PowerShell or cmd.exe without Git for Windows' `usr/bin` on PATH — which is the default state of a Windows machine with Git installed.\n\n**Sibling.** Task `66866236` covers `date -Is` failing on BSD date in the same bodies. Different construct, same class, and the two can be fixed in one pass over `packages/core/assistant-assets/skills/`.\n\n**Possible solutions.**\n1. *Recommended.* Write the message to a temp file and use `git commit -F <file>`. Works in every shell with no Git-Bash-only commands, and preserves the trailer bytes exactly — which is the property that matters, since the trailer is asserted byte-identical against `packages/core/commit-trailers.js` by `tests/e2e/skill-commit-isolation.test.js`. Cost: two lines of skill prose per body. Risk: the skill must also say to clean the temp file up.\n2. Name both forms — heredoc for POSIX, a PowerShell here-string alongside. Cost: more prose in five files; risk: the assistant picks the wrong one for its shell, and PowerShell here-strings have their own trap (the closing `'@` must sit at column 0, so an indented code block silently breaks). Also leaves cmd.exe uncovered.\n3. Repeated `-m` flags. Portable, but not viable — it destroys the trailer block, as above.\n\n**Verification note for whoever picks this up.** Do not verify the fix from Git Bash. That is the environment in which the current, broken instruction already passes, so a green run there proves nothing. Run it from PowerShell with `sh` unresolvable — the state the acceptance criteria pin."
