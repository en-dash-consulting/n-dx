description: "Verdict: must-fix downgraded to should-fix (severity medium) — real and unguarded, but the triggering window is narrow. Found by ndx-adversarial-review reviewing commit 0c23335f (\"fix(hench): suspend the commit-msg watcher while the review pass runs\"), which introduced the suspension this item reports a hole in.\n\n0c23335f makes processSuccessfulResult call ctx.commitWatcher?.cancel() (cli-loop.ts:1368) before runAdversarialReviewPass spawns, so the auto-commit timer cannot fire mid-review. But cancel() is not atomic with respect to a timer that has ALREADY fired.\n\nFailure scenario. The timer fires at time T; tryAutoCommit() clears its `if (cancelled) return` guard (commit-msg-watcher.ts:108) and awaits `git commit -F` (commit-msg-watcher.ts:134-137, 30s timeout). At T+epsilon processSuccessfulResult calls cancel() (commit-msg-watcher.ts:97-105): it sets cancelled = true, clears an already-fired timer (a no-op), and does nothing about the in-flight commit — the call site at commit-msg-watcher.ts:154 is `tryAutoCommit().catch(...)`, fire-and-forget, with no promise retained and no awaitable settle. The reviewer then spawns while `git commit` is still running. Two outcomes:\n\n(a) The commit lands mid-review. HEAD moves, the repairs split from the work they repair, and the HEAD-moved guard at cli-loop.ts:1104-1112 does NOT report it: that guard runs synchronously immediately after cancel(), so it reads the pre-commit HEAD and stays quiet. The operator gets no warning at all.\n\n(b) The reviewer's own git invocation collides with the auto-commit on .git/index.lock. `git commit -F` fails; the `finally` at commit-msg-watcher.ts:142-144 unlinks the message file anyway while autoCommitted stays false; performCommitPromptIfNeeded therefore skips the didAutoCommit() branch and returns at the `!existsSync(msgPath)` early return (shared.ts:1520) printing nothing. Executor work and reviewer repairs are both left uncommitted and the executor's authored commit message is destroyed — silently.\n\nRefutation attempted: looked for an in-flight guard, a retained promise, an awaitable cancel, or a post-cancel didAutoCommit() re-check before the spawn. None exists. The HEAD-moved guard at cli-loop.ts:1104 is the only detector in this path and it fires too early to observe an in-flight commit.\n\nReachability (Pass 2): `ndx work --review`, when the timer expires within roughly the last 30 seconds before the suspension — i.e. the executor wrote .hench-commit-msg.txt about commitMsgTimeoutMs ago (default 300_000) and the completion gate has just finished. Narrow, but nothing detects or prevents it, and outcome (b) loses work.\n\nAlready covered? No. No test exercises it: the regression test added by 0c23335f (review-watcher-suspension.test.ts) cancels before the timer can fire, which is the clean case.\n\nSolutions:\n(A, recommended) Retain the tryAutoCommit() promise in the watcher and expose it — either make cancel() return it, or add `settle(): Promise<void>`. Then `await ctx.commitWatcher?.cancel()` before spawning the reviewer, re-check didAutoCommit(), and if it fired, re-capture startingHead so the review scope and the HEAD-moved warning are both correct. Cost: roughly 10 lines plus a test. Risk: in the rare firing case the pre-review step waits up to 30s for the commit to finish — acceptable next to a review pass measured in minutes.\n(B) Pass timeoutMs: 0 whenever --review is on. Closes the window completely and is the simplest change, but also removes the crash-net for the executor phase, which 0c23335f deliberately kept. Rejected for that reason.\n(C) Re-capture startingHead after cancel() and move the HEAD-moved check to after a settle. Reports the problem but does not prevent the concurrent git operations, so it does not address outcome (b).\n\nRecommend A. Note that outcome (b) is amplified by a separate pre-existing defect in tryAutoCommit's unlink-on-failure behaviour, filed under the Commit Message Timeout feature."
