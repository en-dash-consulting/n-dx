description: "Reproduced deliberately, twice, by running additional `vitest run` processes against packages/web concurrently:\n\n    FAIL tests/unit/server/routes-hench-execute.test.ts\n         > broadcast on execute > broadcasts execution progress events when task is triggered\n    AssertionError: expected [ 'completed', 'failed' ] to include 'starting'\n      at tests/unit/server/routes-hench-execute.test.ts:401\n\nMechanism, and it is entirely in the test. Line 379 is `await new Promise((r) => setTimeout(r, 200))` with the comment \"Wait for process to spawn and complete/fail (no real hench binary in test env)\". The test then asserts the FIRST broadcast is `starting` and the LAST is terminal (`completed`/`failed`). Under load the spawn has not failed yet within 200ms, so only the `starting` broadcast has arrived and first === last. The assertion is sound; the 200ms is the bug.\n\nThis is the same class as the lost-update guard investigated in ff501eb1 — an assertion whose correctness depends on a wall clock — but here the wall-clock bound really is the whole story: no production behaviour is implicated, the route and the broadcast are fine, and a clean single run passes 3077/3077.\n\nHow it first appeared: a `pnpm -r validate` reported 1 file / 4 tests failed in packages/web while a second vitest happened to be running against the same package. That run's output scrolled before the names were captured; the reproduction above names one of them. Whether the other three were in this file or elsewhere is unknown — worth a second look under load, since a fix aimed only at this test may leave siblings with the same shape.\n\nFix: wait on the terminal broadcast rather than a duration — poll `broadcastMessages` for a state in `[\"completed\",\"failed\"]` with a generous ceiling, or expose a promise the route resolves when the child exits. Then the test is bounded by the machine's actual speed instead of asserting one."
