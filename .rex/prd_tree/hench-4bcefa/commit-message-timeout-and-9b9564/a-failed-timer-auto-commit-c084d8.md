The auto-commit timer expires with a non-empty .hench-commit-msg.txt and staged work. `git commit -F` at commit-msg-watcher.ts:134-137 fails — a rejecting pre-commit hook, a gpg signing failure, or .git/index.lock held by a concurrent git process. The catch at 140-141 logs via detail() only, and the `finally` at 142-144 unlinks the message file regardless of outcome. autoCommitted is never set, so it stays false. Control later reaches performCommitPromptIfNeeded, which skips the didAutoCommit() branch (shared.ts:1501, false) and then hits `if (!existsSync(msgPath)) return;` at shared.ts:1520 — the file it needs was just deleted. It returns having printed nothing.\n\nNet result: the staged work is never committed, the executor's authored commit message is permanently gone, and the operator sees no warning on either path — only a detail() line that is easy to miss in a long run log. The staged files then ride the next run's `git add -A` and get attributed to unrelated work.\n\nRefutation attempted: checked whether the empty-file handling added by task 283175 covers this. It does not — that path returns early at commit-msg-watcher.ts:126-131, before the commit is attempted, and is about an empty message rather than a failed commit. Also checked whether performCommitPromptIfNeeded can recover from the deleted file: it cannot, both surviving routes (1520 and the didAutoCommit branch) depend on either the file or the flag, and the failure sets neither.\n\nReachability (Pass 2): does not reproduce in the n-dx repo itself — core.hooksPath is unset, .git/hooks contains no active hooks, and there is no .husky directory. But hench runs against arbitrary user projects, where husky pre-commit hooks are common, and gpg signing via commit.gpgsign is a normal configuration. The index.lock variant is also reachable from within n-dx via the concurrent-git race tracked on item 63cbcc45-1985-49fb-978f-1215e6af092e, which this defect amplifies: there, a lock collision turns a recoverable mid-review commit into lost work plus a destroyed message.\n\nSolutions:\n(A, recommended) Only unlink on success, or when the failure is specifically \"nothing to commit\" (where the file is genuinely useless). On any other failure, keep the file and emit an info() warning naming the staged count, so performCommitPromptIfNeeded can still present the message and the operator can still see the state. Cost: a few lines plus tests for the three outcomes. Risk: a stale message file survives into the next run — but the pre-run commit gate already handles a dirty tree with a message file present, so this is the safer failure direction.\n(B) Distinguish exit codes and retry once after a short delay for the index.lock case specifically. Narrower and more code; does not help the hook or gpg cases.\n(C) Keep the unlink but set a distinct flag (e.g. autoCommitFailed) and have performCommitPromptIfNeeded warn on it.
