description: "Fix inconsistent token accounting between the per-item rollup and the dashboard Usage page (GitHub #294). Today the rollup reports `input + output + cache` as a single conflated total (~23M for a run whose real work was ~40K), while the dashboard Usage page counts only `input + output` (~40K) — a ~575× divergence for the identical runs. The fix is NOT to pick one number: report the ACTUAL token usage, broken out by type, consistently on both surfaces. No cost/pricing math (we cannot estimate per-model cache prices reliably).\n\n## Context — architecture\n\nTwo independent aggregators exist:\n- **rex domain tier:** `packages/rex/src/core/item-token-rollup.ts` walks the PRD tree and sums each hench run's tokens into the item it targeted, rolling up to ancestors. Its `ItemTokenTuple` is `{ input, output, cached, total }` where `tokensFromRecord` (~line 219) computes `cached = cacheCreationInput + cacheReadInput` and `total = input + output + cached`. Consumed by MCP `get_token_usage` and the dashboard.\n- **web tier:** `packages/web/src/server/routes-token-usage.ts` (`extractHenchEvents`, ~lines 351-395) reads run records for the Usage page but only pulls `tokenUsage.input`/`tokenUsage.output` — it drops cache entirely. `packages/web/src/server/task-usage/incremental-task-usage.ts` (~lines 280-284) is the per-task incremental path and must stay consistent with the rollup.\n\nHench run records (`.hench/runs/*.json`) already carry the raw fields `tokenUsage.input`, `tokenUsage.output`, `tokenUsage.cacheCreationInput`, `tokenUsage.cacheReadInput` (and per-turn `turnTokenUsage[]`) — so no hench changes are needed to source the data. rex is the domain tier and web imports from it; keep rex free of web imports.\n\n## Why the numbers diverge (not a counting error)\n\nWith prompt caching, hench sends a large stable context once (cache-CREATION), then RE-READS it from cache every subsequent turn (cache-READ). A 30-turn run re-reading a ~750K-token context accumulates ~22M cache-read tokens — the same context counted once per turn. These reads are real usage but represent re-reads of identical context, not new work. Collapsing them into one `total` makes a 40K-of-work task read as 23M; dropping them (dashboard) hides real usage. Both surfaces should instead show the same itemized breakdown.\n\n## Fix direction\n\n1. **rex rollup — break cache into its two real types.** Change `ItemTokenTuple` from `{ input, output, cached, total }` to carry `input`, `output`, `cacheCreation`, `cacheRead`, and `total` (= input + output + cacheCreation + cacheRead — the true actual usage). Update `tokensFromRecord`, the self/descendant attribution, and the ancestor roll-up so all four components roll up independently. `ItemTokenTotals` (self / descendants / total) carries the same breakdown. Expose `input + output` as a derived \"work\" convenience if helpful. This is a breaking change to a shared type — update EVERY consumer in the monorepo and keep typecheck green (search for `ItemTokenTuple`, `.cached`, `aggregateItemTokenUsage`, `get_token_usage`).\n\n2. **web dashboard — read and surface cache, consistently.** Extend `extractHenchEvents` (and the Usage-page event/aggregation types) to also read `cacheCreationInput` / `cacheReadInput` from run records (and per-turn if `turnTokenUsage` carries them; otherwise attribute the run-level cache totals once per run, not per turn, to avoid double counting). Surface input, output, cache-write, cache-read as distinct fields. Make `incremental-task-usage.ts` use the same breakdown so the per-task number matches the rollup.\n\n3. **Consistency is the acceptance bar.** After the change, for the same set of runs the rollup (`get_token_usage`) and the dashboard Usage page must report the SAME component numbers. The ~575× \"inflation\" disappears because cache-read becomes an explicit, labeled line rather than silent bloat — the total is still the true actual sum, just itemized.\n\n## Acceptance criteria\n\n1. The rollup exposes `input`, `output`, `cacheCreation`, `cacheRead` as distinct fields, with `total` = their sum; all four roll up from descendants to ancestors correctly.\n2. The dashboard token-usage path reads and surfaces cache-creation and cache-read (no longer input+output only), attributing run-level cache totals without double-counting across turns.\n3. For a fixed set of run records, the rex rollup and the web Usage aggregation report identical `input`/`output`/`cacheCreation`/`cacheRead`/`total` values — no divergence.\n4. No cost or pricing math is introduced; only raw token counts.\n5. All existing consumers of `ItemTokenTuple` compile and behave correctly; regression tests cover the new breakdown in both rex and web.\n\n## Testing guidance (TDD, red→green)\n\n- rex unit: extend `packages/rex/tests/unit/` item-token-rollup tests — a synthetic run with input/output/cacheCreation/cacheRead aggregates into the four components and a correct total, and rolls up to ancestors.\n- web unit/integration: extend the token-usage tests under `packages/web/` so `extractHenchEvents`/Usage aggregation surfaces cache components and matches the rollup for the same synthetic runs (assert equality of the two aggregations — this is the anti-regression for the divergence itself).\n- Windows note: normalize CRLF in any file-content comparisons.\n\n## Constraints\n\n- TDD: write failing tests first, then implement.\n- Tier boundary: rollup/breakdown types live in `packages/rex` (domain); `packages/web` imports from rex — do NOT add web→rex-internal or rex→web imports. No hench changes are required.\n- Do NOT regress the just-landed #303 / #302 / #293 work.\n- No pricing/cost estimation — actual token counts only.\n- `pnpm --filter rex typecheck && pnpm --filter @n-dx/web typecheck` and the rex + web unit suites must stay green (modulo the ~38 pre-existing Windows CRLF/path failures tracked in #301)."
