description: "When a hench shell command hits its timeout, only the intermediate shell is killed. The command itself survives, keeps running, and keeps writing to the workspace — while hench has already told the agent the command stopped.\n\nMEASURED, NOT INFERRED. Probe against the built hench (packages/hench/dist/tools/exec-shell.js) on Windows, running a worker that writes a marker file once per second, with a 400ms timeout:\n\n  hench reported:              \"Command timed out after 400ms\"\n  node processes before/after:  3 -> 4      (the inner process outlived the call)\n  marker immediately after:     absent\n  marker 3.5s later:            present, content \"tick 4\"\n\nFour writes landed AFTER hench reported the command had stopped. A separate probe using a 60s sleep showed the same orphan plus an rmdir that failed continuously for 52,686ms — the handle is held for as long as the orphan lives, so waiting it out is not a remedy.\n\nCAUSE. execShell (packages/hench/src/tools/exec-shell.ts) runs exec(\"sh\", [\"-c\", command], { timeout }), and the llm-client exec wrapper relies on Node's execFile timeout. That timeout signals the direct child only — the sh — so the process sh started is orphaned rather than terminated. This is the same tree-kill asymmetry that motivated terminateTree in packages/core/child-lifecycle.js, but on the hench path, where nothing performs the tree kill.\n\nWHY THIS MATTERS BEYOND TIDINESS. An autonomous agent treats \"timed out\" as \"this command is finished\" and proceeds — reading files, running the next command, committing. A build, codemod, or test run still writing underneath that decision can corrupt the state the agent then reads. Timeouts are also how a runaway command is normally stopped, so \"stopping\" needs to actually stop it.\n\nNOT WINDOWS-ONLY, though Windows is where it was caught. On POSIX the orphan survives too; it is merely less visible because POSIX allows unlinking files that are still open, so no EBUSY draws attention to it. Fixing this should use the platform-appropriate mechanism on both: a process-group kill on POSIX, taskkill /T on Windows.\n\nARCHITECTURAL CONSTRAINT — read before reaching for terminateTree. terminateTree lives in packages/core (orchestration tier) and CANNOT be imported here: the allowed direction is core -> hench -> llm-client, so neither hench nor llm-client may import from core. Options, roughly in order of preference:\n\n1. Move the tree-kill primitive down into @n-dx/llm-client (foundation) and have packages/core/child-lifecycle.js consume it from there. One implementation, correct tier, no duplication — but it touches the termination code that other cross-OS tasks also touch, so sequence it against those.\n2. Stop delegating to execFile's timeout: have execShell own the timer and perform the tree kill itself when it fires. Contained to hench, but duplicates the kill logic that already exists in core.\n3. Spawn the command detached in its own process group and kill the group on timeout. Closest to the POSIX-native answer, still needs a Windows branch.\n\nDo not \"fix\" this by lengthening the timeout or by having callers wait for the orphan — the requirement is that a reported timeout means the command has actually stopped.\n\nEVIDENCE OF THE TEST-SIDE SYMPTOM, for context: this was found while fixing 8e79620a (Windows EBUSY in temp-dir cleanup). That task's stated fixes — await the child's exit, or retry the rmdir — were both disproven by the probes above; its four test failures were a symptom of this defect. The tests were made to pass by keeping the orphan's lifetime short (see TIMEOUT_ORPHAN_LIFETIME_MS in packages/hench/tests/unit/tools/shell.test.ts), which is a test-side accommodation, not a fix for this."
