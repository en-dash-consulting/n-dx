description: "**This task is part of PR 2 of 4** (Prepare task phase 2: the `run` field; PR #537, moved back to draft for this change).\n\n## Why (decision TP15, Ryan, 2026-10-06)\nSaved run settings must be vendor-agnostic. Ryan creates PRD items while connected to Claude and may execute them with hench/ndx connected to Codex (or the reverse). A saved `\"model\": \"claude-opus-5-5\"` means nothing on Codex: today it would be skipped with a warning and the intent (\"run this on the strong model\") is lost. Decision: **option C — a portable tier plus optional per-vendor model pins.** This matches TP10 (recommend a tier, resolve per vendor) and TP13 (editable tier in the Prepare task modal). Nothing reads `run` yet and #537 is unmerged, so there is nothing to migrate: drop `model` and `reviewModel` outright.\n\n## New `run` shape\n```\nrun: {\"tier\":\"heavy\",\"models\":{\"claude\":\"claude-opus-5-5\",\"codex\":\"gpt-5.6-sol\"},\"review\":true,\"reviewTier\":\"standard\"}\n```\n| key | type |\n|---|---|\n| tier | \"light\" \\| \"standard\" \\| \"heavy\" (llm-client `TaskWeight`) — portable intent, resolved per vendor at run time |\n| models | object keyed by vendor (`LLM_VENDORS` from @n-dx/llm-client: claude, codex, google, local), each value a model id string ≤256 bytes; at least one entry when present; an exact pin for that vendor only |\n| reviewTier | same values as `tier`, for the reviewer |\n| reviewModels | same shape as `models`, for the reviewer |\n| provider, permissionMode, review, reviewOptional, skipTestGate, maxTurns, tokenBudget, contextNotes | unchanged |\n`model` and `reviewModel` are REMOVED from the saved block (writers reject them as unknown keys; the lenient store still round-trips an old or hand-written block untouched).\n\nResolution, implemented later in PR 3 (do NOT implement it here; just document it): on vendor V the agent model is CLI `--model`/`--V-model` > `run.models[V]` > `run.tier` (via `llm.tiers.V.<tier>`, then the built-in tier table) > `hench.models.V` > `llm.*` > default. The reviewer: `--review-model` > `run.reviewModels[V]` > `run.reviewTier` > `llm.V.reviewModel` / `llm.reviewModel` > vendor default. `permissionMode`, `provider` and `maxTurns` apply only when the active vendor supports them and are otherwise skipped with a one-line note.\n\n## What to change (rex + docs; no hench, no web viewer behaviour)\n1. **Schema** (packages/rex/src/schema/v1.ts `RunSettings`, `RUN_SETTING_KEYS` and the byte/turn constants; packages/rex/src/schema/validate.ts `RunSettingsSchema`, `validateRunSettings`): replace `model`/`reviewModel` with `tier`, `models`, `reviewTier`, `reviewModels`. Import `LLM_VENDORS` and the `TaskWeight` values from @n-dx/llm-client (rex already depends on it; domain → foundation is allowed). `models`/`reviewModels`: strict record over known vendor names only (an unknown vendor name is rejected by writers with the valid list), non-empty strings ≤ 256 UTF-8 bytes, and an empty object normalises to absent (like `{}` for the whole block). Keep the store/document schema lenient exactly as PR 2's must-fix left it (a malformed or newer block round-trips and warns; it never blocks other writes).\n2. **Order:** `RUN_SETTING_KEYS` in a sensible command-line-ish order: tier, models, provider, permissionMode, review, reviewTier, reviewModels, reviewOptional, skipTestGate, maxTurns, tokenBudget, contextNotes.\n3. **Writers:** MCP `add_item`/`edit_item` schema descriptions (packages/rex/src/cli/mcp.ts ~:186 and ~:204) and `rex update --run` help/examples (packages/rex/src/cli/help.ts ~:149) list the new keys; the example becomes `--run='{\"tier\":\"heavy\",\"review\":true}'` plus one with `models`.\n4. **Contract test** tests/e2e/run-options-contract.test.js (~:19-40, :124-132): the saved keys are no longer \"hench task-scope options + contextNotes\". Restate the contract: the saved keys equal hench's task-scope RUN_OPTIONS with `model` → {tier, models} and `reviewModel` → {reviewTier, reviewModels}, plus `contextNotes`; keep the dashboard `RunOptions` (launch-time options sent to execute) unchanged — an explicit model id per launch is still correct there because a launch knows its vendor.\n5. **Viewer mirror type** packages/web/src/viewer/components/prd-tree/types.ts `RunSettingsData` and packages/web/tests/unit/server/type-consistency.test.ts.\n6. **Tests:** validator unit tests (tier enum; models with known/unknown vendor, empty object, over-long id; old `model` key rejected by writers), round-trip with tier + models + reviewTier + reviewModels, MCP and `rex update --run` tests updated.\n7. **Docs:**\n   - docs/architecture/prd-folder-tree-schema.md (the `run` section ~:200-215 and the summary table): new keys, the vendor-agnostic rationale, and the PR 3 resolution order above (marked as how `ndx work` will apply it).\n   - docs/packages/rex.md, docs/guide/mcp.md, rex help.\n   - packages/core/assistant-assets/project-guidance.md add_item/edit_item lines (→ CLAUDE.md): mention tier/models briefly.\n   - AGENTS.md (Ryan's rule: assistant docs reach AGENTS.md too): update the Rex bullet in `renderAgentsMd()` (packages/core/assistant-assets.js, \"When to Use Each Server\") to say the run block saves a portable tier plus optional per-vendor model pins, then regenerate with `node -e \"import(process.cwd()+'/packages/core/assistant-assets.js').then(m=>require('fs').writeFileSync('AGENTS.md', m.renderAgentsMd()))\"` (not `ndx init`); `git diff AGENTS.md` must show only that bullet changing.
