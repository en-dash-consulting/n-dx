description: "**This task is part of PR 2 of 4** (Prepare task phase 2: the `run` field). Found by /ndx-adversarial-review of feat/090-r0-loe-fidelity...feat/090-run-field. Verdict: **must-fix** (severity high: a hard stop on every PRD write, reachable by a hand edit of a documented field or by a newer ndx version).\n\n## Failure scenario (reproduced)\nIn a scratch project built with this branch's rex: two tasks A and B. Hand-edit Task A's file to add `run: {\"model\":\"claude-opus-5-5\",\"reviw\":true}` (a typo of `review`). `loadDocument()` still succeeds (one parser warning), but `handleEditItem(store, dir, {id: B, priority: \"high\"})` on the UNRELATED Task B fails with `Error: Invalid document after mutation: [... \"run\" ...]`. Every store write in the workspace is refused until someone finds and fixes Task A: MCP edits, `rex update`, dashboard writes, and hench's completion write at the end of any `ndx work` run.\n\nSecond trigger, no typo needed: when a later ndx adds a `run` key (e.g. a per-task vendor, decision TP6), items saved by the newer version make every older ndx on another branch, machine or teammate refuse all writes to that tree. A strict nested schema plus whole-document validation on write makes the field forward-incompatible.\n\n## Why it happens\n- packages/rex/src/schema/validate.ts (~:177): `PRDItemSchema` includes `run: RunSettingsSchema.optional()`, which is `.strict()` with bounds.\n- packages/rex/src/store/folder-tree-parser.ts (~:892, `const run = fm[\"run\"]`): the parser deliberately keeps a non-empty plain-object `run` even when it fails the schema, warning \"writes are refused until it is fixed\".\n- packages/rex/src/store/file-adapter.ts (~:301, `validateDocument(doc)` in the transaction): every write runs load → mutate → `validateDocument` over the whole document, so one item's bad block fails every write.\n- The PR 2 task spec asked for \"writing a malformed run through the store is rejected\"; the implementation met it at document level, which is the bug.\n\n## Reachability\nReal. The `run` format is documented (prd-folder-tree-schema.md, rex help) and hand-editing front matter is normal. Version skew between worktrees and teammates is normal too.\n\n## Proposed solutions\n1. **(Recommended) Validate at the writers, keep the document lenient.** In `PRDItemSchema`, accept any plain object for `run` (e.g. `z.record(z.string(), z.unknown()).optional()`). Keep `validateRunSettings` as the gate in every writer that accepts `run` from a caller: MCP add_item/edit_item, `rex update --run`, and (PR 4) `PUT /api/hench/prep/:taskId`. The store round-trips a malformed or newer block unchanged; the parser keeps its warning (reword it: \"ndx work ignores this block until it is fixed\"). PR 3's hench resolver already ignores an invalid block with a warning. Cost: small; a few tests flip. Risk: a buggy writer that skips `validateRunSettings` could store a bad block, but it would not break anything else.\n2. Parser drops an invalid `run` (with a warning). Not recommended: the next save of that item silently deletes the user's hand edit, and newer keys are lost on older versions.\n3. Validate `run` only on items the write actually changed. More invasive (needs per-item change tracking in `runTransaction`); no benefit over 1.\n\n## Also update\n- docs/architecture/prd-folder-tree-schema.md:209 currently states writes are refused until the block is fixed — rewrite to the new contract (writers reject bad input; the store keeps a malformed or newer block as written; ndx work ignores an invalid block with a warning).\n- The schema comment in validate.ts (~:85-92) and the parser warning text.\n- Tests that assert a store write refuses a malformed block: change them to assert (a) the store round-trips it unchanged, (b) an unrelated item can still be written, (c) MCP/CLI writers still reject the same input.\n- Changeset: amend or add a @n-dx/rex patch changeset line if the user-visible behaviour description changes.\n\n## Note (2026-10-06)\nRe-verified after merging #518 (perf/deterministic paths, now on this branch via PR 1): the reproduction still fails the same way. #518's fast write path (packages/rex/src/store/targeted-update.ts) renders through the same `renderItemIndexMd`; check that it also accepts a lenient `run` once the document schema changes, and cover it in a test if `performance.fastWrites` is a separate path.\n\n## Operator note\nCommands are pre-approved only when they START with npx, node, npm, git or vitest.
