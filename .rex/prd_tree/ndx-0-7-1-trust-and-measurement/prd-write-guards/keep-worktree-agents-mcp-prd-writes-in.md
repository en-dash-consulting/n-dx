description: "A hench run in ~/ndx-core/n-dx-071-capture (run 0b919f4f) completed WM2042, and the agent's MCP update_task_status wrote the task file in ~/ndx-core/n-dx, the main checkout, on whatever branch it had checked out. Cause: a Claude local-scope MCP registration for the repository (claude mcp add --scope local, the pre-0.7 ndx init path) pins rex and sourcevision to the main checkout's absolute path (node .../packages/rex/dist/cli/index.js mcp /Users/.../n-dx), and Claude Code applies it to sessions started in the repository's other worktrees, shadowing the tracked .mcp.json that resolves '.' per worktree. The per-workspace PRD lock cannot help: the write never reaches the right workspace. Fix candidates: hench's spawned session passes an explicit MCP config (or --strict-mcp-config) naming its own worktree; ndx init stops writing absolute-path local registrations and offers to remove existing ones; ndx doctor or the run pre-flight warns when a registration pins a different worktree.\n\nChosen approach (2026-09-25). Claude runs only; the Codex adapter is unchanged. (a) In buildClaudeCliArgs (hench agent/lifecycle/adapters/claude-cli-adapter.ts), which every spawn uses including the review pass's --resume/--fork-session, pass --mcp-config <file> plus --strict-mcp-config. The file defines two stdio servers: rex = process.execPath <cli.js> rex mcp <absProjectDir>, and sourcevision = process.execPath <cli.js> sv mcp <absProjectDir>. Here <cli.js> is the core CLI named by NDX_CLI_PATH. Anchoring on the core CLI takes rex and sourcevision from the install that launched the run, whatever its layout (workspace checkout or node_modules). It needs no new rex-gateway export, which keeps the gateway ceiling free for C2, and no hench→sourcevision dependency, since hench does not depend on sourcevision. It also makes the agent's rex version match hench's, which PR C2's completion hold relies on. (b) NDX_CLI_PATH is inherited by child processes, and resolveCliPath in hench process/toolchain-identity.ts returns it without checking where it came from. Use it only after confirming it belongs to the same install as the running hench, for example by comparing realpaths of the install roots derived from NDX_CLI_PATH and from hench's own import.meta.url. Otherwise treat the run as standalone. (c) Standalone hench run (no usable NDX_CLI_PATH): keep today's behaviour, passing no MCP flags, and print a warning naming the reason. Do not guess a rex or sourcevision path. (d) Write the MCP config as a per-run file under .hench/runs/ (for example <runId>.mcp.json), which is gitignored and never committed, with absolute paths only. Never pass it as inline JSON: cmd.exe quoting on Windows is the hazard the Windows branch of buildClaudeCliArgs already works around. (e) The server names stay exactly rex and sourcevision. The agent's MCP tools are permitted by .claude/settings.json entries such as mcp__rex__update_task_status and mcp__sourcevision__*, not by --allowed-tools, so a renamed server hits permission denials in -p runs. (f) The changeset states that --strict-mcp-config drops the operator's user-scope and other MCP servers from autonomous Claude runs. (g) The agent's shell rex/ndx/n-dx commands still resolve from PATH, which bypasses C2's completion hold on the CLI path. Prepend to the agent's PATH a per-run directory of shims (rex, ndx, n-dx) that exec process.execPath <NDX_CLI_PATH> with the matching subcommand, under the same same-install rule as (b). If that is out of scope, record it in this task's resolution and in the changeset as a known gap. (h) This covers criterion 1 for Claude runs only. Criteria 2 and 3 are still required in this task. Criterion 2: ndx init stops writing an absolute-path local-scope registration, and it reports an existing one along with the claude mcp remove command. Criterion 3: the run pre-flight warning, which still matters for Codex runs and interactive sessions. Test for criterion 1: under an overridden HOME, a fake ~/.claude.json holds a local-scope entry pinning another checkout, and the test asserts on the spawn argv and on the generated config's absolute project directory.\n\nConstraints that apply to every n-dx change: cross-package imports go only through the package's gateway module (hench: src/prd/rex-gateway.ts and src/prd/llm-gateway.ts; web: src/server/rex-gateway.ts and src/server/domain-gateway.ts) and tests/e2e/architecture-policy.test.js enforces an export ceiling on those gateways; orchestration scripts in packages/core spawn CLIs and never import packages; every user-facing change carries a changeset using the scoped package name (@n-dx/hench, @n-dx/rex, @n-dx/web, @n-dx/core, @n-dx/sourcevision, @n-dx/llm-client) with a patch bump; run pnpm preflight before opening the PR."
