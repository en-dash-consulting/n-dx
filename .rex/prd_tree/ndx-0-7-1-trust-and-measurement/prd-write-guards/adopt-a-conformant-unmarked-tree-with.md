description: "DECIDED 2026-09-22 — build it. This is no longer an open question; the owner accepted the adopt-and-notice behaviour described below, in preference to two alternatives that were considered and rejected. It must land before 0.7.1 publishes, because as things stand the release refuses every existing repository's first PRD write.\n\nRejected alternative 1: leave the hard refusal and bump @n-dx/rex to a minor so the required operator action rides a minor release. That makes the release 0.8.0, which collides with the roadmap's planned 0.8.0 content, so renumbering is the more disruptive lever.\n\nRejected alternative 2: leave the hard refusal but have the gates detect it, auto-run rex migrate-slugs and resume the interrupted run. For the case this task covers — a conformant tree with no marker — that is a subprocess and resume machinery built to accomplish a one-line write, since migrate-slugs on a conformant tree renames nothing and only records the marker. Recording it directly at the guard is the same outcome without the scaffolding. Auto-running migrate-slugs on a genuine mismatch is a separate question, captured separately; see the task about auto-migrating a non-conformant tree.\n\n---\n\nWM2092 replaced the absent-marker adopt branch in packages/rex/src/store/slug-rule-guard.ts with a hard refusal: any non-empty tree carrying no slugRule marker is refused by the store guard, rex validate, the ndx work pre-gate and the dashboard Execute gate until rex migrate-slugs is run. The reasoning is sound in the abstract — absence cannot be distinguished from a marker an older build stripped, and a path scan can only recognise a rule this build can reproduce — but the cost falls on the wrong people.\n\nThe marker is unreleased. It was introduced in commit 82efe050 (PR #384); no git tag contains it and npm's latest @n-dx/rex is 0.7.0. So no published build has ever written one, and every existing install hits the refusal on its first PRD write after upgrading to 0.7.1.\n\nSLUG_RULE_VERSION = 2 describes a path rule that landed 2026-08-26, before the 0.5.1 release (2026-08-28). So every tree written by 0.5.1 through 0.7.0 — effectively every tree in the wild — already has rule-2 paths and no marker. For those users rex migrate-slugs renames nothing: it records the marker and exits, which is byte-for-byte the end state the adopt branch produced for free. Trees older than 0.5.1 carry rule-1 paths and were refused by the previous guard too, so nothing changes for them. The hard stop therefore lands entirely on the population for whom the command is pure ceremony, in a patch release.\n\nWhat the refusal does buy is visibility: an operator learns the marker went missing rather than having it silently re-adopted, and 0.7.0 MCP servers — the exact build that caused the observed incident — will keep running alongside 0.7.1 for the whole release window. A loud notice buys that same visibility without the stop.\n\nRestore the adopt branch for the conformant case and keep the refusal for everything else: scan the paths of an unmarked non-empty tree, and if the scan is clean, record the marker and print a prominent one-line notice naming rex migrate-slugs as the way to verify. Refuse on a non-conformant scan or a marker mismatch, exactly as today.\n\nThe counter-argument recorded in slug-rule-guard.ts is that a future build could re-slug a tree that then scans clean, so this build would stamp its marker onto paths it did not write. That hazard is real but not yet possible: there is no rule 3, and whoever introduces one edits SLUG_RULE_VERSION in that same commit and can flip adopt back to refuse there. It is a hazard controlled at the moment it becomes possible rather than one worth paying for now.\n\nImplementation notes: in packages/rex/src/store/slug-rule-guard.ts, assertSlugRuleWritable currently returns early only when parseFolderTree reports no items and otherwise throws; restore the findNonConformingSlugs scan for the unmarked case and return when it finds nothing, leaving the refusal path for a non-empty mismatch list. Apply the same split to checkTreeConformance, whose absent-marker branch returns a refusal before the scan runs. Reverse the corresponding error in cmdValidate at packages/rex/src/cli/commands/validate.ts so a clean scan reports a notice rather than an error, and keep SLUG_RULE_MARKER_MISSING and missingMarkerExplanation for the cases that still refuse. Update the tests that WM2092 rewrote: packages/rex/tests/unit/store/slug-rule-guard.test.ts, packages/rex/tests/unit/cli/commands/validate.test.ts, packages/hench/tests/integration/prd-tree-conformance-gate.test.ts and packages/web/tests/unit/server/routes-hench-execute-tree-conformance.test.ts. Amend the WM2092 changeset rather than adding a second one, since neither has shipped — its \"Upgrading costs one rex migrate-slugs per repository\" paragraph becomes wrong. Leave the tree-meta key preservation from WM2092 untouched; it is the half of that change that is not in question. Constraints that apply to every n-dx change: cross-package imports go only through the package's gateway module (hench: src/prd/rex-gateway.ts and src/prd/llm-gateway.ts; web: src/server/rex-gateway.ts and src/server/domain-gateway.ts) and tests/e2e/architecture-policy.test.js enforces an export ceiling on those gateways; orchestration scripts in packages/core spawn CLIs and never import packages; every user-facing change carries a changeset using the scoped package name with a patch bump; run pnpm preflight before opening the PR."
