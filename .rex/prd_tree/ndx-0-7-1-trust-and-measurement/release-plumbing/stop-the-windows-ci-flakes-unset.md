description: "HOTFIX for 0.7.1 CI. Test and config only — no production code changes.\n\nThe CLI Smoke (Windows) job fails intermittently with two distinct symptoms, and both have a known cause and an existing in-repo remedy that simply is not applied.\n\n**Cause 1 — hookTimeout is never set anywhere in the repository.** Vitest's default hookTimeout is 10000ms. Every config that bothers to raise testTimeout leaves hookTimeout at that default, so a beforeEach gets 10s while the test it prepares gets 30s (120s at the root). The hench integration hooks run mkdtemp, initGitFixtureRepo, and git add plus git commit as subprocesses; on a Windows runner that legitimately exceeds 10s under load. Observed as `Error: Hook timed out in 10000ms.` at between-task-uncommitted-guard.test.ts:45.\n\nCurrent state:\n- vitest.config.js — testTimeout 120000, hookTimeout UNSET\n- packages/hench/vitest.config.ts — testTimeout 30_000, hookTimeout UNSET\n- packages/rex/vitest.config.ts — testTimeout 30000, hookTimeout UNSET\n- packages/sourcevision/vitest.config.ts — testTimeout 30_000, hookTimeout UNSET\n- packages/web/vitest.config.ts — both UNSET (web has also failed this job: run 35761150216)\n- packages/llm-client/vitest.config.ts — both UNSET\n\nSet hookTimeout alongside testTimeout in each, at no less than the testTimeout already chosen there. A hook that is allowed less time than its test is an oversight rather than a policy, and fixing it centrally removes the whole failure class.\n\n**Cause 2 — RM_RETRY exists, is documented, and is bypassed.** packages/hench/tests/helpers/index.ts:275 defines `RM_RETRY = { maxRetries: 10, retryDelay: 100 }` and cleanupProjectDir spreads it. Its doc comment already explains exactly this failure: on Windows a directory cannot be removed while any process holds a handle inside it, a just-signalled git child has not necessarily let go by teardown, and POSIX allows unlinking an open file so the retry only ever engages on Windows. It even instructs \"Spread this into an fs.rm call when the directory is not a setupProjectDir project; use cleanupProjectDir when it is.\"\n\n30 hench test files use git subprocesses and call fs.rm directly without RM_RETRY or cleanupProjectDir, across 45 rm() call sites. Both files observed failing on CI are in that set: integration/between-task-uncommitted-guard.test.ts and integration/withdraw-completion-ancestors.test.ts. Observed as `Error: EBUSY: resource busy or locked, rmdir 'C:\\\\Users\\\\RUNNER~1\\\\AppData\\\\Local\\\\Temp\\\\hench-between-task-guard-iWKv1z'`.\n\nThe full list is reproducible with: for f in $(grep -rl \"rm(.*recursive: true\" packages/hench/tests --include=\"*.ts\"); do grep -q \"git \" \"$f\" && ! grep -q \"RM_RETRY\\\\|cleanupProjectDir\" \"$f\" && echo \"$f\"; done\n\nApply RM_RETRY (or switch to cleanupProjectDir where the directory is a setupProjectDir project) at every one of those call sites. Do not swallow errors — the helper's doc is explicit that failures must propagate, because a swallowed failure turns a leaked temp directory into an invisible problem.\n\n**Deliberately out of scope**, decided with the owner: the same rm-retry sweep across rex (8 retry usages across 113 files), web (39) and sourcevision (0). Those are real exposure but ~200 files, too broad to land as a hotfix. Capture separately if wanted.\n\n**Do not** change any test's assertions, expectations, or behaviour. This task makes existing tests survive a slow, handle-holding Windows filesystem; a test that needs its logic changed to pass is a different finding and should be reported rather than edited.\n\nEvidence this is pre-existing and not caused by PR #397: CLI Smoke (Windows) is the failing job on main runs 35774856252 (4/5 suites passed — failed: @n-dx/hench, EBUSY), 35761150216 (failed: @n-dx/web) and 35683995074. On PR #397 an earlier run failed in withdraw-completion-ancestors.test.ts and a later one in between-task-uncommitted-guard.test.ts — different files, same symptoms, which is environment rather than defect. Neither file is touched by #397.\n\nConstraints that apply to every n-dx change: cross-package imports go only through the package's gateway module; orchestration scripts in packages/core spawn CLIs and never import packages; run pnpm preflight before opening the PR."
