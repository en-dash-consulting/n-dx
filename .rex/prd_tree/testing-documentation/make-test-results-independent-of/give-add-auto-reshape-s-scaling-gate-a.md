The parser gate does; the reshape gate is thin.\n\nMEASURED (Windows 11, Node v22, three runs each, via temporary logging since these tests only print on failure):\n\n  gate                        bound   observed               worst margin   min-of-N?\n  folder-tree-parser.test.ts  45.3x   6.23 / 6.15 / 7.22x    6.3x           yes (fastestMs)\n  add-auto-reshape.test.ts    12.0x   1.08 / 3.62 / 7.33x    1.64x          NO - single shot\n\nThe parser gate is healthy, and its Windows ratio matches the 6.3x recorded when it was written. So cross-OS ratio drift is NOT a general property of these gates - it is specific to the prd_tree write path, where Windows per-item syscall cost grows with directory size. Do not generalize the write-path finding to other gates without measuring.\n\nTWO DEFECTS in add-auto-reshape.test.ts, test \"scoped pass cost grows sub-quadratically with sibling count\":\n\n1. NO MIN-OF-N. timeScopedPass times each size exactly once, with no warm-up:\n     const smallMs = await timeScopedPass(\"Small Epic\", smallSiblings);\n     const largeMs = await timeScopedPass(\"Big Epic\", largeSiblings);\n   Hence the 6.8x swing across three runs (small read 204.7ms, 68.3ms, 59.9ms - the first is cold, and it is the one that makes the ratio look best, which is backwards). A load spike on the large reading inflates the ratio directly, and the bound sits only 1.64x above the worst reading observed. Not hypothetical: this same file's previous absolute budget was observed timing out at the 30s test limit under full-suite load.\n\n2. SHARED-TREE CONFOUND. Both epics are built in the same store, so the 100-sibling pass runs against a tree that already holds the 25-sibling epic (26 extra items) while the 25-sibling pass does not. Any component of runScopedConsolidationPass cost that tracks total tree size rather than sibling count inflates the large reading only, biasing the ratio upward - toward false failure. The sibling-count claim the test makes is therefore not cleanly isolated.\n\nSUGGESTED FIX: give timeScopedPass the fastestPhases/fastestMs treatment (min of 3, first pass as warm-up) as used in write-path-profile.test.ts and folder-tree-parser.test.ts, and build each size in its own store (or subtract a baseline) so sibling count is the only variable. Then re-derive the bound from three runs and record the measurements in the comment, as the sibling files do.\n\nWATCH THE COST. The test already carries a raised 60s timeout because setup dominates (~14s of tree building for ~190ms of timed work). Min-of-3 multiplies the timed part cheaply but re-running setup would not be cheap - build the trees once, time the pass three times.\n\nDO NOT simply raise the bound to 4x or 6x. Bounds must be verified in both directions: on write-path-profile a 6x bound picked from clean baselines let a real n^2 degradation pass at 200.9x, and only injecting the fault revealed it. Whatever bound is chosen here, degrade runScopedConsolidationPass quadratically and confirm the gate fails."
