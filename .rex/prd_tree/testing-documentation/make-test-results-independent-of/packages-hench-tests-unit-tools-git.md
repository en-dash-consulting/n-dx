description: "**Severity:** high — **Verdict:** must-fix (captured from /ndx-adversarial-review of branch `chore/pr-329-review-followups`, 2026-08-25)\n\n**Failure scenario.** `toolGit` calls `execShell` (`packages/hench/src/tools/git.ts:19`), which runs `exec(\"sh\", [\"-c\", cmd])`. `sh` is not on PATH in a stock Windows shell — it ships with Git for Windows at `C:\\Program Files\\Git\\usr\\bin\\sh.exe`, which Git Bash exposes and PowerShell/cmd.exe do not. So the spawn fails, `exec` returns `exitCode: 1` with empty output, and the tool formats the string `\"Exit code: 1\"`. Seven cases in `packages/hench/tests/unit/tools/git.test.ts` then fail with assertions like `expected 'Exit code: 1' to contain 'branch'` — no mention of a shell anywhere in the message.\n\n**Reproduced both ways on the same commit, no code changes between runs:**\n- PowerShell: `pnpm test` in `packages/hench` → **7 failed / 2923 passed**, all seven in `git.test.ts` (`runs git status`, `runs git rev-parse`, `runs git log on repo with commits`, `runs git diff`, `uses guard allowlist instead of hardcoded list`, `returns (no output) for commands with empty output`, `captures stderr output`).\n- Git Bash (`sh` at `/usr/bin/sh`): `npx vitest run tests/unit/tools/git.test.ts` → **25/25 pass**.\n\n**Evidence.** `packages/hench/tests/unit/tools/git.test.ts:52` (first failing case) through `:242`; `packages/hench/src/tools/git.ts:19`; `tests/shell-spawn-inventory.md:3` and the table at `:36-42`.\n\n**Relation to prior work.** Task `be8e19c3` (\"Make the tests' sh-on-PATH dependency explicit instead of failing opaquely\") is marked **completed**, and this finding contradicts two of its claims. Its `resolutionDetail` says \"Audited every shell-spawning test (found 28 cases in 5 files ...)\" and \"Verified from both PowerShell (0 failures)\". `git.test.ts` is a sixth file with 7 unguarded cases, and PowerShell produces 7 failures. Its first acceptance criterion — \"An audit lists every test that spawns `sh` (or another shell) and states, per site, whether it is guarded — the two known files were found incidentally, so the true count is unverified\" — is therefore not satisfied. By `tests/shell-spawn-inventory.md`'s own taxonomy this is a *kind: under test* site: hench's git tool genuinely shells out on every platform, so a missing `sh` means `git` tool calls do not work on that machine either.\n\nThis is filed as a new task rather than an edit to `be8e19c3` because the fix is a distinct code change to a file that item never touched. Whether `be8e19c3` should be moved off `completed` is a separate decision, deliberately not taken by this review.\n\n**Refutation attempted.** Checked whether the other `execShell`-referencing test files are also unguarded: `packages/hench/tests/unit/validation/completion-timeout.test.ts:14` and `packages/hench/tests/unit/agent/review-gate-rollback.test.ts:57` both `vi.mock` the exec boundary, so no process is created and no guard is needed. `packages/hench/tests/unit/process/exec.test.ts:124` inspects a fake spawn's arguments, as the inventory already records. `git.test.ts` is the only missed site.\n\n**Reachability.** Every `pnpm test` run in `packages/hench` from PowerShell or cmd.exe — the default shell on the platform this project is developed on. CI is unaffected (the Windows runner has Git's bin directory on PATH), so this misleads a local developer while the pipeline stays green — the exact distribution `be8e19c3` was written to eliminate.\n\n**Possible solutions.**\n1. *Recommended.* Guard the seven cases with the existing helper and add the inventory row. Cost: roughly 15 lines, mirroring what was already done for `shell.test.ts` and `test-runner.test.ts`. Risk: none — the guard only changes what happens when `sh` is absent.\n2. Add an automated completeness check for the inventory: scan test files for real shell spawns and fail when one has no inventory row. Cost: a new e2e test plus a detector that can tell a real spawn from a mocked one. Risk: false positives on mocked call sites. This is the durable fix and is worth doing *in addition to* (1), not instead of it — (1) alone leaves the next missed site just as invisible."
