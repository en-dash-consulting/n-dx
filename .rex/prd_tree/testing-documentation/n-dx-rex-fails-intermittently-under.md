description: "Seen four times, on 2026-09-10 and 2026-09-11, always while validating unrelated work on feat/portable-prd-bundle: `pnpm test` reports `FAIL @n-dx/rex` and exits non-zero, while `pnpm --filter @n-dx/rex test` immediately afterwards passes in full and a repeat `pnpm test` also passes. Same commit, both outcomes.\n\n**CORRECTION to the original capture.** It claimed this \"reproduces only under the recursive run, where `pnpm -r` executes package suites in parallel\". That is wrong on both counts and would misdirect the next attempt. The root `test` script is `node scripts/run-all-tests.mjs`, which runs each suite **sequentially** — a `for...of` loop over synchronous `execFileSyncCli` calls with `stdio: \"inherit\"`. There is no cross-package parallelism to contend for. Whatever differs about `pnpm test` is that rex runs *after* the root suite and the earlier packages, not alongside them.\n\n**Prior art in the repo.** `scripts/run-all-tests.mjs`'s own docblock says the runner exists partly because \"with **rex's load-sensitive tests failing**, hench and web ... never executed at all\", masking 32 hench and 7 web failures. So this suite has a known history of load-sensitive failure, and someone has hit it before.\n\n**Sightings.** Three on 2026-09-10. The fourth on 2026-09-11, validating the `--replace` sync-pointer fix (3b33aff4): `pnpm test` failed on rex, `pnpm --filter @n-dx/rex test` then passed standalone at 239 files / 5039 tests, and a re-run of the full suite passed 6/6. The change under validation touched only `core/prd-bundle.ts` and its tests, so it was not the cause. Every sighting has been on a machine with other work in flight.\n\n**Reproduction attempts, all negative:**\n- 10 consecutive idle `pnpm test` runs — clean.\n- The rex suite alone under full CPU saturation (12 spinners on 8 cores, load average ~22, run stretched from ~25s to ~10min) — all 238 files and 5023 tests passed. **CPU pressure alone does not cause it**, which substantially weakens the \"timeout under load\" theory the original capture leaned on.\n- 25 consecutive runs of `file-lock.test.ts` + `stale-save-guard.test.ts` in isolation — clean.\n- A reviewer independently ran six consecutive standalone rex suites — all green.\n\n**The failing assertion has still never been seen, and the fourth sighting shows why.** It was lost for the same reason as the first three: the failing `pnpm test` was run without redirecting output, so by the time the failure was noticed only the summary line remained. Every deliberate capture attempt has been on a quiet machine and come back green; every organic failure has been un-redirected. That is the whole gap.\n\n**Named candidates**, from reading rather than from a capture — unconfirmed:\n- `tests/unit/store/file-lock.test.ts`, \"serializes concurrent withLock calls\": a bare `await new Promise(r => setTimeout(r, 5))` is the *only* thing making `p1` acquire the lock before `p2`, and the assertion is a strict `expect(order).toEqual([1, 2, 3])`. If p1's acquisition (a filesystem write) slips past that 5 ms margin, the order inverts. The same 5 ms pattern appears twice more in that file.\n- `tests/integration/concurrent-write-lost-update.test.ts`: `Promise.race([addPromise, sleep(2_000)])` bounds a real write at two seconds; if the write exceeds it under load the race resolves via the sleep and the test proceeds on a false premise.\n\n**Next step is capture, and it is now an operational habit rather than an experiment:** always redirect, e.g. `pnpm test > run.log 2>&1`, so the next organic occurrence is diagnosable rather than lost. Better still, have `run-all-tests.mjs` retain each suite's output to a file so no one has to remember. Do not chase it with synthetic CPU load — that has been tried, does not reproduce, and is disproportionate on a developer machine."
