description: "Seen three times on 2026-09-10 while validating unrelated work on feat/portable-prd-bundle: `pnpm test` reports `FAIL @n-dx/rex` and exits non-zero, while `pnpm --filter @n-dx/rex test` immediately afterwards passes in full (238 files, ~5023 tests) and a repeat `pnpm test` also passes. Same commit, both outcomes.\n\n**CORRECTION to the original capture.** It claimed this \"reproduces only under the recursive run, where `pnpm -r` executes package suites in parallel\". That is wrong on both counts and would misdirect the next attempt. The root `test` script is `node scripts/run-all-tests.mjs`, which runs each suite **sequentially** — a `for...of` loop over synchronous `execFileSyncCli` calls with `stdio: \"inherit\"`. There is no cross-package parallelism to contend for. Whatever differs about `pnpm test` is that rex runs *after* the root suite and the earlier packages, not alongside them.\n\n**Prior art in the repo.** `scripts/run-all-tests.mjs`'s own docblock says the runner exists partly because \"with **rex's load-sensitive tests failing**, hench and web ... never executed at all\", masking 32 hench and 7 web failures. So this suite has a known history of load-sensitive failure, and someone has hit it before.\n\n**Reproduction attempts, all negative:**\n- 10 consecutive idle `pnpm test` runs — clean.\n- The rex suite alone under full CPU saturation (12 spinners on 8 cores, load average ~22, run stretched from ~25s to ~10min) — all 238 files and 5023 tests passed. **CPU pressure alone does not cause it**, which substantially weakens the \"timeout under load\" theory the original capture leaned on.\n- 25 consecutive runs of `file-lock.test.ts` + `stale-save-guard.test.ts` in isolation — clean.\n- A reviewer independently ran six consecutive standalone rex suites — all green.\n\nThe failing assertion has still never been observed. Every organic failure happened while other work was in flight in the same session; every deliberate attempt has been on a quiet machine.\n\n**Named candidates**, from reading rather than from a capture — unconfirmed:\n- `tests/unit/store/file-lock.test.ts`, \"serializes concurrent withLock calls\": a bare `await new Promise(r => setTimeout(r, 5))` is the *only* thing making `p1` acquire the lock before `p2`, and the assertion is a strict `expect(order).toEqual([1, 2, 3])`. If p1's acquisition (a filesystem write) slips past that 5 ms margin, the order inverts. The same 5 ms pattern appears twice more in that file.\n- `tests/integration/concurrent-write-lost-update.test.ts`: `Promise.race([addPromise, sleep(2_000)])` bounds a real write at two seconds; if the write exceeds it under load the race resolves via the sleep and the test proceeds on a false premise.\n\n**Next step is still capture, and the cheap high-yield move has not been tried:** make the failure legible when it next happens organically, rather than hunting it. Piping `pnpm test` through `tee` in normal use, or having `run-all-tests.mjs` retain per-suite output to a file, means the next organic occurrence is diagnosable instead of lost to scrollback — which is how all three sightings were lost. Do not chase it with synthetic CPU load; that has been tried and does not reproduce."
