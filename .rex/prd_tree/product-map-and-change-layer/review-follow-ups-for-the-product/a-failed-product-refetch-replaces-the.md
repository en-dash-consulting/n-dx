description: "Verdict: should-fix (adversarial review of 54cc1a166, run 9842f0db). Scenario: on a v2 project the Product page is loaded and a capability page is open. A rex:prd-changed frame triggers a refetch of GET /api/rex/product (packages/web/src/viewer/views/product-pages.ts, useProductRead). If that refetch answers 500 (routes-rex/product.ts:351 returns errorResponse(500) when the model load throws, e.g. read mid-write) or the fetch rejects, setLoad({state:\"error\"}) replaces the ready data. ProductPage checks `load.state !== \"ready\"` before `capabilityId`, so the open capability page vanishes into an alert with no Back button, and the map stays replaced until the next frame or a reload. Before 54cc1a166 a page fetched only on mount, so a loaded page could not regress to an error. Reachable whenever a refetch fails after a v2 write; how often a read hits a half-written tree is unverified. Options: (a) on a refetch (revision > 0) failure, keep the last ready data and surface the error inline, e.g. a small stale notice (small; recommended); (b) only move ProductPage's capabilityId check ahead of the map's load state (smaller, fixes only the lost-capability half).\n\nFolded in on 2026-10-13: 4965aeda (The Ask panel proposes v2 merges that the v1 rule allows and the v2 rule then refuses at apply) covered the same surface and was carried here with its acceptance criteria."
