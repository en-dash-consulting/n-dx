description: "Review 2026-10-12, PR #690 should-fix 1 (CONFIRMED at unit level; the MCP path traced line by line).\n\nDefect: packages/rex/src/core/change-selection.ts:119 filters candidates with `!options.excludeIds?.has(u.node.id)`, so on v2 a claim excludes a unit only by its own id. The split rule (core/change-completion.ts:229, addTask) turns an in-flight task-less change's work into a new in_progress task, and the claim stays on the change.\n\nFailure scenario:\n1. Worktree A runs update_task_status {id: C, status: \"in_progress\"} on task-less change C, which takes the claim on C (acquireClaim).\n2. A's agent breaks the work down with add_item {type: \"task\", parentId: C}. addTask splits: the new task T becomes in_progress, and C goes back to pending.\n3. Worktree B calls get_next_task. excludeIds is {C}. T is not excluded, and because it is in_progress it ranks above pending work. B gets T, and update_task_status T in_progress grants B a fresh claim on T.\n4. Both worktrees now work the same unit, the double-pick claims exist to prevent (T4's criterion \"claims from other worktrees skipped\"). B's answer even lists C under skippedClaimed while handing out C's only work.\nReproduced: after addTask, findNextWork(tree, {excludeIds: new Set([\"C\"])}) returns task T in change C.\n\nFix (preferred): in findActionableWork, skip a unit when its change, or any change enclosing it, is in excludeIds. This also covers a claim on a container. (Alternative: move the claim from the change to the task on split, in the add_item v2 path when result.split is set.)"
