description: "Found while fixing the PRD-tree snapshot temp-file race (task 607c72c9) on 2026-09-12. That fix removed the ENOENT failure mode entirely — 0 ENOENT failures in 60 isolated runs of tests/integration/import-bundle-transaction.test.ts on fix/autonomous-run-reliability, against the ~18% measured before it. The same test still fails ~3% (2 of those 60 runs), now with a different error, so it is a second defect the same test exposes rather than a regression of the first.\n\nFAILURE SCENARIO\ntests/integration/import-bundle-transaction.test.ts > 'does not lose either writer's items when two imports run concurrently' fails with:\n\n  Stale-save guard: this save would delete 1 item written after the document being saved was loaded\n    - From Second Bundle [bbbbbbbb-...] (.../.rex/prd_tree/from-second-bundle.md)\n\nOne import's transaction loaded a document that does not contain the other writer's item, yet saved after that item was on disk. Both imports run their read-modify-write inside store.withTransaction, which loads and writes inside withLock — so for this to happen the two processes must both have been inside the critical section. The lock did not serialize them.\n\nHYPOTHESIS — NOT YET CONFIRMED, verify before fixing\npackages/rex/src/store/file-lock.ts publishes the lock with writeFile(lockPath, content, { flag: 'wx' }). That is open(O_CREAT|O_EXCL) followed by a separate write(), so the file exists with zero bytes for a short window. A competing acquirer that reads it in that window gets '' from readFile, decodeLock returns null, and isLockStale (~line 131) classifies 'Malformed = stale'. acquireLock then unlinks the live holder's lock file and takes its own — two writers in the critical section.\n\nThis is the same symptom the comment at file-lock.ts:138-147 records as already fixed: age-based staleness was removed precisely because it let a second writer in alongside a live one and the loser's save was rejected by the stale-save guard. The malformed-file branch is a second route to the same place, and it was not covered by that fix.\n\nConfirm before changing anything — e.g. have isLockStale record which branch reclaimed a lock, and assert it never reports the malformed branch across a few hundred concurrent acquisitions. If the malformed branch is not the cause, the next suspects are releaseIfOwner racing a reclaim, and resolveStore performing a load outside the transaction.\n\nSOLUTION SKETCH\nMake publication atomic so the name never exists with incomplete content: write the lock body to a sibling temp file, link() it to lockPath (link fails EEXIST when the name is taken, giving the same exclusion as 'wx'), then unlink the temp. Failing that, stop treating a malformed lock as immediately stale — re-read after a short delay and reclaim only if it is still malformed, which distinguishes a half-written lock from a genuinely corrupt one.\n\nNote the stale-save guard itself behaved correctly here: it refused a save that would have destroyed another writer's item. The defect is upstream, in the mutual exclusion that should have made the situation impossible.\n\nConventions: cross-package imports through the gateway modules; pnpm test from the repo root before declaring done."
