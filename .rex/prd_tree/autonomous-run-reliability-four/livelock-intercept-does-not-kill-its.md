description: "Found by the CLI Smoke (Windows) CI job on PR #370, runs 34689369208 and 34703337769. macOS and Build & Validate pass; Windows is the only failing job, and it has failed on every push since the livelock feature landed. Severity: high — it blocks the PR, and if the diagnosis is right the livelock protection does not work on Windows at all.\n\nFAILURE SCENARIO\npackages/hench/tests/integration/livelock-cli-spawn.test.ts, case \"kills a child that keeps making the same call, and says which call\", fails on windows-latest with two errors:\n\n  Error: Test timed out in 20000ms.       (at tests/integration/livelock-cli-spawn.test.ts:93)\n  Error: EBUSY: resource busy or locked, rmdir 'C:\\Users\\RUNNER~1\\AppData\\Local\\Temp\\hench-test-livelock-spawn-bATwx4'\n\nThe timeout is the real failure: await spawn(\"same\", 4) never resolves. The EBUSY is the consequence — afterEach cannot remove the temp directory because the stand-in CLI is still running and still holding it. The stand-in only exits when it is signalled, so the child outliving the test means the intercept never killed it.\n\nhench suite on Windows: 1 failed, 3433 passed. rex, sourcevision, web, core and llm-client all pass on Windows.\n\nCANDIDATE CAUSES — confirm before fixing, do not guess\nBoth kill sites in packages/hench/src/agent/lifecycle/cli-loop.ts (the plan-mode intercept near line 1025 and the livelock intercept near line 1047) call proc.kill with SIGTERM and have no Windows branch.\n\n1. Signal semantics. Node cannot deliver SIGTERM to a process on Windows. The stand-in CLI installs a SIGTERM handler that clears its interval and exits 143; that handler can never run on Windows. Node's kill should still terminate the child via TerminateProcess, so this alone may not explain a hang — establish empirically whether the child dies.\n2. Detection never fires. If the adapter does not map the stand-in's stream-json into tool_use events on Windows (chunk boundaries differ on Windows pipes, so a partial-line buffer bug shows up there and not on macOS), the detector never reaches its threshold, kill is never called, and the child loops until the timeout. This would mean the livelock feature is inert on Windows, which is much worse than a test bug.\n3. The close handler never resolves. The promise resolves from the child close event; if a pipe stays open after termination the await never returns even though the process died.\n\nDistinguishing them is the first task. Add temporary diagnostics to the test (assert the detector fired, assert the child pid is gone) and run it on a Windows runner before changing production code.\n\nSOLUTION\nFix whatever cause is confirmed, in production code, not by relaxing the test. If the intercept cannot terminate a child on Windows, give it a platform-correct path and cover both intercepts, since plan-mode interception uses the identical pattern and has no equivalent real-spawn test. If detection is inert on Windows, that is a defect in the feature this PR adds and must be fixed and covered.\n\nDo not skip the test on Windows to get the PR green. A skip would hide exactly the platform gap this job exists to find. If the work turns out to be larger than this PR should carry, say so and split it, leaving the test failing and the PR honest about why.\n\nACCEPTANCE CRITERIA\n- CLI Smoke (Windows) passes on this branch.\n- The livelock intercept is proven to terminate a real child on Windows, not merely to choose a signal.\n- The temp directory is removed cleanly in afterEach, with no EBUSY.\n- If the plan-mode intercept shares the defect, it is fixed and covered too.\n- Changeset for @n-dx/hench (patch).\n\nConventions: hench must not import node:child_process directly (tests/e2e/architecture-policy.test.js enforces it); cross-package imports go through the gateway modules. Run pnpm test from the repo root before declaring done."
