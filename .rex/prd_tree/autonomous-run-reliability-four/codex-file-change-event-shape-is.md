description: "Found by ndx-adversarial-review on commit 08c24213. Severity: medium. Verdict: should-fix.\n\nFAILURE SCENARIO\npackages/hench/src/agent/lifecycle/adapters/codex-cli-adapter.ts:434-442 credits a Codex patch as livelock progress by matching three string assumptions about the codex exec --json stream: the item discriminator is exactly 'file_change', the failure marker is item.status === 'failed', and the changed paths live in item.changes. None of these is backed by a recorded stream, a vendored schema, or a version pin — they come from the issue text that described the defect.\n\nIf any assumption is wrong (item type named differently, or file changes reported as a command_execution of apply_patch rather than a distinct item), the branch never fires. Every Codex --auto run then keeps the exact bug the commit claims to fix: an edit-then-retest loop is stopped at the sixth identical shell({\"command\":\"pnpm test\"}) and the task is deferred as livelocked. The failure is silent — no warning, no unmapped-event counter — and the task, the changeset and GH #370 finding 3 all read as resolved.\n\nThe tests cannot catch this. packages/hench/tests/unit/agent/codex-cli-adapter.test.ts:497-556 and packages/hench/tests/integration/codex-livelock-progress.test.ts:44-51 construct their input from the same assumption as the code under test, so they pass whether or not the assumption matches the vendor. This is the whole repo's pattern for Codex events (tests/fixtures/cross-vendor-runtime.ts holds hand-built RuntimeEvents, not captured output), but for file_change the consequence is uniquely invisible: a wrong shape for command_execution would show up as empty tool-call lists in run records, whereas a wrong shape here changes nothing an operator can see.\n\nREACHABILITY\nEvery 'ndx work' run on the Codex vendor. Entry point: spawnWithAdapter -> processLine -> adapter.parseEvent (cli-loop.ts:1011), livelock intercept at cli-loop.ts:1038.\n\nRELATED, SAME ROOT CAUSE\nThe same unverified ordering assumption underwrites the accumulator pairing. applyRuntimeEvent (cli-loop.ts:352-360) attaches a tool_result to toolCalls[last]. If Codex can complete a file_change between a command's item.started and item.completed, the test's stdout is attributed to the apply_patch record instead of the shell record. The current code assumes codex items never interleave; that assumption is untested and should be settled by the same capture.\n\nSOLUTION OPTIONS\n1. Capture a real stream and assert against it (recommended). Run one small codex exec --json task that edits a file and runs a command, save the JSONL to packages/hench/tests/fixtures/, and drive codexCliAdapter.parseEvent over every line. Cost: one Codex run plus a fixture file. Risk: the fixture pins one codex-cli version, so it needs a version comment and will drift. Benefit: settles the discriminator, the status vocabulary, the changes field and the item ordering in one pass, and gives the repo its first real Codex wire-format test.\n2. Make the failure loud instead of silent. Count item.completed types the adapter did not map and surface the tally at end of spawn. Cost: small. Risk: noise on every unmapped-but-uninteresting item type. Weaker than option 1 because it detects the drift rather than preventing it, but it would have caught this class of defect without a Codex run.\n3. Do nothing and accept the risk. Cheapest, and the current behaviour already fails safe in the drift direction that matters (an unrecognised status string credits progress rather than withholding it). Rejected because it leaves the commit's entire value resting on an unverified string.\n\nRecommend option 1, optionally with option 2 as a cheap backstop."
