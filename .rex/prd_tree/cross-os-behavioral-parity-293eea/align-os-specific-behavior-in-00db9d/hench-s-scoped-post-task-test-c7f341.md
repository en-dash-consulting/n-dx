description: "A PRODUCTION defect, not a test-fixture problem. Found while fixing the path-separator test assertions (task 7c897777), which flagged this as a possibility to verify rather than assume. It is real, and it is proven end to end.\n\nTHE CHAIN:\n1. findRelevantTests() returns OS-native paths — on Windows, \"src\\agent\\loop.test.ts\". That is correct\n   for its own use: it stat()s them, and Windows accepts backslashes.\n2. buildScopedCommand() (packages/hench/src/tools/test-runner.ts:217-253) joins those paths into a\n   COMMAND STRING, e.g. `vitest run src\\agent\\loop.test.ts`.\n3. runPostTaskTests() executes it via execShellCmd (test-runner.ts:361), which is\n   `exec(\"sh\", [\"-c\", command])` in packages/llm-client/src/exec.ts:141-146 — a POSIX shell,\n   UNCONDITIONALLY, on every platform.\n4. sh treats each backslash as an escape, so the path collapses.\n\nMEASURED on Windows 11, each step separately:\n  sh -c 'echo src\\agent\\loop.test.ts'                      ->  srcagentloop.test.ts\n  sh -c 'npx vitest run tests\\unit\\store\\run-log.test.ts'   ->  \"No test files found, exiting with code 1\"\n  vitest with a filter matching nothing                     ->  exit code 1\n\nCONSEQUENCE: on Windows, every scoped post-task test run reports `passed: false` regardless of whether\nthe code is fine, because the filter is destroyed before vitest sees it. hench therefore believes its own\nwork broke the tests after essentially every task with a scopeable runner.\n\nWorth stating what it is NOT: not a silent pass. vitest exits 1 on an empty filter match, so this\nsurfaces as a false FAILURE rather than false confidence — the less dangerous of the two, but it makes\nthe post-task gate useless on Windows and would push an agent into pointless remediation loops.\n\nAlso note vitest itself is NOT the problem: a backslash filter passed directly (no shell) matches\ncorrectly — verified with `npx vitest run 'tests\\unit\\store\\run-log.test.ts'`, which found the file and\nran 11 tests. The corruption happens strictly at the sh -c boundary.\n\nFIX OPTIONS, and the choice deserves thought rather than the first thing that works:\n1. Normalize to forward slashes where the paths become a COMMAND rather than a filesystem argument —\n   i.e. in buildScopedCommand, not in findRelevantTests. Forward slashes work as vitest/jest/mocha\n   filters and survive sh unharmed, and it keeps findRelevantTests correct for its stat() use. This is\n   the narrowest change.\n2. Stop routing test commands through a POSIX shell on Windows. More correct in principle and it would\n   fix the whole class rather than this instance, but execShellCmd is shared (llm-client, hench,\n   sourcevision) so the blast radius is much wider — and `sh` genuinely exists on most Windows dev boxes\n   via Git for Windows, which is why nothing else has broken loudly.\n3. Quote each path inside the command string. Fragile: it re-invents the quoting problem the\n   spawn-hardening epic centralized in win-spawn.js, and this is a shell STRING not an argv.\n\nPrefer (1) and record why, since (2) is a defensible larger cleanup that should be its own decision.\n\nVERIFICATION MUST BE END TO END, not just a unit assertion on the returned string: run a real scoped\npost-task test on Windows against a project with a vitest runner and confirm the tests actually execute\nand the reported pass/fail reflects them. A unit test asserting the command string contains forward\nslashes would pass while the real flow stayed broken if some other step re-introduces separators."
