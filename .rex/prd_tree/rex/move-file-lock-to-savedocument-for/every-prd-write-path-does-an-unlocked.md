description: "**Severity:** high — data loss, silent. Captured 2026-08-25 at the user's request while filing findings from /ndx-adversarial-review.\n\n**Failure scenario.** `rex reorganize` (or `prune`, `reshape`, `plan`, `analyze`) calls `store.loadDocument()`, spends seconds to minutes computing a restructuring — an LLM round trip in most cases — then calls `store.saveDocument(doc)` with the snapshot it loaded. `saveDocument` is a **full replacement**: `packages/rex/src/store/contracts.ts:74` states \"the stored state after the call is exactly the document passed in\". Any item written by another process during that window — an MCP `add_item` from an assistant, a `hench` status update, a second CLI command — is present on disk when the long writer starts serializing and absent afterwards. No error, no conflict, no log line. The item is simply gone.\n\n**Evidence — the fix already exists and nothing calls it.** `packages/rex/src/store/contracts.ts:190-204` defines `withTransaction`, documents it as holding the lock \"for the entire duration, preventing concurrent writers from interleaving\", and names the callers by name:\n\n> \"CLI commands that do their own load→mutate→save (reorganize, prune, reshape) should use this instead of calling loadDocument/saveDocument directly.\"\n\nA repo-wide search for `.withTransaction(` returns **three hits, all in test files** (`packages/rex/tests/integration/prd-md-no-write-regression.test.ts:225`, `packages/rex/tests/integration/markdown-only-writes.test.ts:151`, `packages/rex/tests/unit/store/prd-aggregation.test.ts:393`). Zero production call sites.\n\nMeanwhile the direct `saveDocument` call sites number more than twenty, including all three commands the contract names:\n- `packages/rex/src/cli/commands/reorganize.ts:173`\n- `packages/rex/src/cli/commands/reshape.ts:93`, `:349`\n- `packages/rex/src/cli/commands/prune.ts:319`, `:481`, `:689`\n- `packages/rex/src/cli/mcp-tools.ts:136`, `:312`, `:370`, `:594` — the MCP write tools themselves\n- plus `move.ts:37`, `fix.ts:39`, `remove.ts:135/182/219`, `update.ts:79`, `add-reshape.ts:812`, `backfill-commit-attribution.ts:219`, `create-from-recommendations.ts:328/413`, `validate.ts:295`\n\n**Why the existing lock does not cover this.** `packages/rex/src/store/file-lock.ts` is real and sound — in-process mutex, ownership-token compare-and-delete, stale detection — and `FolderTreeStore.addItem`/`updateItem`/`removeItem` (`folder-tree-store.ts:88-126`) correctly wrap load→mutate→save in `withLock`. But that only protects mutations made *through those three convenience methods*. A caller that loads the document itself, holds it across a long computation, and calls `saveDocument` takes no lock over the span. Note also that `FolderTreeStore.saveDocument` (`folder-tree-store.ts:71`) takes **no lock at all**, unlike `FileAdapter.saveDocument` (`file-adapter.ts:472-475`), which acquires the folder-tree lock when not already inside a transaction. Even that adapter's lock would not help here: serializing the write is not the same as serializing the read-modify-write.\n\n**Relation to prior work.** Three completed items in this area, none of which closes this gap:\n- `8d4e7984` \"Add file-level locking to PRD store to prevent concurrent write corruption\" — added the lock to the convenience methods.\n- `9fa85475` (this item's parent) \"Move file lock to saveDocument for complete write safety\" — its stated problem is exactly this one (\"CLI commands like reorganize, prune, and reshape do their own loadDocument → mutate → saveDocument outside those methods, bypassing the lock entirely\") and its chosen remedy was \"the lock should be at the saveDocument level (or a withTransaction API)\". The `withTransaction` API was built; the call sites were never migrated to it, so the feature closed with its own acceptance criterion — \"CLI commands (reorganize, prune, reshape) are protected from concurrent MCP writes\" — unmet.\n- `5d0a6670` hardened `file-lock.ts` internals against a flaky test. Correct work, different layer.\n\n**How the hazard is handled today.** As operator discipline, not enforcement. The root `CLAUDE.md` concurrency contract marks `ndx plan` + `ndx work` and `ndx ci` + `ndx work` as ❌, and states: \"Never invoke MCP write tools while a CLI command that writes to the PRD is running in the background (e.g., `reorganize`, `prune`, `reshape`, `analyze`, `plan`). The last writer wins silently — no error, just data loss. Always wait for the background command to complete before making MCP writes.\" That is an accurate description of the defect and a reasonable stopgap, but it puts the invariant in a document a background agent may not have read, guarding a failure mode that produces no signal when violated.\n\n**Reachability.** Any assistant session that runs a PRD-writing command in the background and calls an MCP write tool before it finishes — which the toolchain actively encourages, since `ndx plan` and `ndx reorganize` are long enough that backgrounding them is the natural move. Also two humans in one repo, and `ndx start` + a CLI write.\n\n**Possible solutions.**\n1. *Recommended.* Migrate the read-modify-write call sites to `store.withTransaction`, starting with the three the contract names plus `mcp-tools.ts`. The API and the lock already exist, so this is call-site work, not new machinery. Cost: mechanical but broad — 20+ sites, and the long-running ones need their LLM call kept *outside* the transaction (load a snapshot, compute unlocked, then re-load and re-apply inside the transaction) or the lock will be held for minutes and starve every other writer. Risk: that restructuring is the real work and needs care per command.\n2. Make the lock unavoidable: have `FolderTreeStore.saveDocument` acquire the lock when not inside a transaction, matching `FileAdapter`. Cheap and closes the torn-write window, but does **not** fix the lost update — a stale full-document snapshot still overwrites the concurrent item, just without interleaving. Worth doing as a floor, not as the fix.\n3. Optimistic concurrency: stamp the document with a revision or content hash at load, and reject a `saveDocument` whose base revision no longer matches. Turns silent loss into a loud, retryable failure without holding a lock across an LLM call — the best fit for the long-running commands. Larger change: needs a revision field in the tree metadata and a retry path in every caller.\n4. Keep it as documentation only. Not recommended: the failure is silent and destroys user data, and the guidance lives where an autonomous writer is least likely to consult it.\n\n**Decision to make.** Whether long-running commands should hold the lock across their LLM call (simple, but serializes the toolchain and can block for minutes) or use optimistic concurrency with a re-apply on conflict (better behavior, more machinery). Solution 3 is the better end state; solution 2 is a cheap floor that can land immediately either way."
